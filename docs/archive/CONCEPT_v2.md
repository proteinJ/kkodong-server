## 1. 재정의된 핵심 포지셔닝

**문제의식**: 사람 아이는 유치원·학교로 또래 친구를 만들고 사회화하지만, 반려견은
그 역할을 하는 강아지 유치원(펫데이케어)이 월 20~90만원대로 비싸 접근성이 낮다
(검증됨 — 리앤폴 등 가격 사례, 82cook/블라인드 커뮤니티 불만 확인).

**포지셔닝 문구(카피 레벨로 채택)**: "유치원보다 저렴하게, 우리 강아지의 산책 친구를
만드는 곳"

**핵심 목적 재확인 (2026-07-08, 사용자 결정)**: 유상 산책 대행은 하지 않을 확률이
높으며, 이 플랫폼의 진짜 목적은 "강아지들끼리 친구를 만드는 것" 그 자체다 — 마케팅
카피가 아니라 제품의 존재 이유. 따라서 순수 로지스틱(시간·장소) 매칭만으로는 목적을
충족하지 못한다는 판단 하에, 아래와 같이 절충한다.

**결정된 절충안**: "성향+견종+반경" 다중조건 알고리즘(콜드 스타트 악화 리스크로 HOLD)은
그대로 보류하되, **MVP부터 유저가 직접 입력하는 심플 셀프 필터(크기/나이대/에너지레벨)는
포함**한다 — 복잡한 알고리즘 없이 매칭 풀을 심하게 좁히지 않으면서도 "아무나"가 아닌
최소한의 궁합 신호를 제공. 본격 성향 매칭 알고리즘은 유저 밀도가 임계치를 넘은 이후로
계속 유예(../TICKETS.md Q2).

## 2. 기능 범위 재조정

### 2.1 그대로 유지 (v1 기준)
- 지도 기반 친구 실시간 위치, 산책 파트너 매칭/모집, 1:1·그룹 채팅
- 산책 세션 기록
- 완료 카드(9:16) — **v1 검증에서 이미 Phase 1로 조기 배치 권고됨**, 이번 재검증에서도 변경 없음

### 2.2 새로 추가 — 저비용/저리스크로 확인된 것만 채택
- **매칭 심플 셀프 필터(신규, MVP 포함)**: 유저가 직접 입력하는 크기/나이대/에너지레벨
  정도의 가벼운 필터. 복잡한 알고리즘·자동 계산 없이 "강아지들끼리 친구 만들기"라는
  핵심 목적을 최소한으로 충족. 매칭 풀을 심하게 좁히지 않도록 필터 항목 3개 이하로 제한.
- **반려견 프로필 사진 배경제거("누끼") 기능**: iOS Vision 프레임워크
  (`VNGenerateForegroundInstanceMaskRequest`, iOS 16+)로 온디바이스 구현, 서버 비용 없음.
  단, **핵심 차별화로 내세우지 않고 부가 재미 요소로만 취급** — 아이폰 기본 사진 앱도
  동일 기능을 이미 제공해 체감 차별화가 약하다는 반론 반영. Phase 2 이후 저우선 티켓.
- **예방접종/구충제 D-day 알림**: v1 PET_CARE 영역에 이미 있던 기능. **유저 수동 입력
  날짜 기반**으로 우선 구현(동물등록번호 연동 없이도 완결됨).

### 2.3 보류(HOLD) — 이번 요청에서 제외
- **본격 성향/견종 기반 매칭 알고리즘**: 콜드 스타트 악화 리스크 + 포동(DBTI 성향데이터
  보유) 카피 리스크. 유저 밀도가 임계치를 넘은 이후(Phase 3+)로 재검토. (단, MVP에
  심플 셀프 필터(크기/나이대/에너지레벨)는 포함 — 2.2 참조)
- **초보 견주 전용 커뮤니티 확장**: 포동(44만+ 가입자, 초보 견주 커뮤니티+전문가 상담
  이미 운영 중)과 정면충돌. 별도 커뮤니티 기능으로 확장하지 않고, 기존 "산책 기록
  기반 피드"로 범위를 좁게 유지.
- **동물등록번호 API 연동**: 스펙 실사 완료(../TICKETS.md Q1, 2026-07-08) — 공공데이터포털
  동물등록 조회 API는 예방접종 이력을 반환하지 않음(등록번호·품종·생년월일 등 기본 정보만
  제공). **이 기능은 폐기.** 예방접종 D-day 알림은 유저 수동 입력 기반으로만 구현.

## 4. 수익 모델 — 당근마켓 벤치마킹 반영 (2026-07-08)

**참고 사례**: 당근마켓은 핵심 기능(중고거래)을 수수료 0원으로 완전 무료 유지하고,
그 위에 쌓인 로컬 밀도·체류시간을 별도 레이어(하이퍼로컬 광고)로 수익화한다.
2024년 매출 1,891억원의 99%가 광고였다([당근 보도자료](https://about.daangn.com/company/pr/archive/%EB%8B%B9%EA%B7%BC-2024%EB%85%84-%EB%A7%A4%EC%B6%9C-1891%EC%96%B5-%EC%9B%90-%EC%98%81%EC%97%85%EC%9D%B4%EC%9D%B5-376%EC%96%B5-%EC%9B%90-%EA%B8%B0%EB%A1%9D/)).

**PawWalk 적용**: 핵심 루프(친구 매칭·산책기록·완료카드)는 계속 완전 무료 유지, 수익화는
동네 단위 반려동물 업체 타겟 광고(동물병원·펫샵·미용실·훈련소·유치원) 레이어로 분리.
예방접종 D-day 알림 화면에 "가까운 동물병원" 비즈프로필을 붙이는 식으로 케어 기능과
광고를 연결하면 v1 검증에서 지적됐던 "커머스 축 연결 약함" 문제도 일부 해소된다.

**단, 광고는 후행 지표다**: 당근마켓의 광고 모델은 WAU 1,400만이라는 압도적 밀도가
전제다. PawWalk 초기엔 동네당 유저가 소수일 것이므로 광고 매출은 사실상 0에서
시작한다. 또한 광고주 풀 자체가 동네당 동물병원·펫샵 1~2개 수준으로 당근마켓(전
업종)보다 구조적으로 작다. **따라서 구독(Free/Plus/Pro)이 유저 밀도 없이도 작동하는
유일한 초기 수익 축이며, 광고는 밀도가 쌓인 후에나 의미 있어지는 후행 축으로 로드맵에
배치한다.**

**초기 현금흐름 원칙**: 산책 대행(수수료)이 로드맵에서 사실상 빠지고 광고도 후행
지표가 되므로, 서비스 초창기엔 매출이 거의 없는 게 자연스럽다. 다만 이것이 "적자가
불가피하다"는 뜻은 아니다 — 벤처 투자를 받아 몇 년간 손실을 감수하며 스케일을 태우는
당근마켓식 전략은 외부 자본이 없는 1인 개발 구조에 맞지 않는다. 대신:
- 인프라를 처음부터 트래픽 연동형(usage-based)으로 설계해 매출이 0이어도 고정비 지출이
  거의 없도록 유지
- 구독을 MVP부터 켜두어 소규모로라도 현금 유입을 초기부터 만든다
- "회계상 적자"와 "현금 소진(cash burn)"을 구분해서 추적한다 — 1인 개발자 본인의
  시간(기회비용)은 회계상 잡히지 않지만 실질적 비용이므로 별도로 인지한다

**백엔드 인프라 결정 — 2차 수정 (2026-07-08, 최종)**: ~~관리형 BaaS(Supabase 전체)
채택~~은 폐기. 사용자가 대학교 학부생이며 목적이 사업이 아니라 **학습(취업 대비
포함)**임을 명확히 함에 따라, 비용/운영 최소화보다 범용 백엔드 개발 경험(한국
채용시장 표준인 Spring/JPA/Spring Security)을 쌓는 쪽을 우선하기로 결정 변경:

- **백엔드 서버: Java Spring Boot** — Controller/Service/Repository/JPA로 직접 구현.
  인증도 Spring Security + 자체 JWT(AT/RT) 발급/갱신/폐기로 직접 구현(Supabase Auth
  미사용)
- **DB: Supabase는 Postgres 호스팅 용도로만 유지** — PostgREST 자동생성 REST, RLS,
  Realtime, Supabase Auth는 전부 사용하지 않음. Spring Boot가 JDBC로 직접 접속
- **인증 관련 재검토**: RLS가 사라지므로 권한 검증은 Spring Boot 서비스 계층 코드에서
  직접 수행. `auth.users`↔`public.users` 트리거 브릿지 패턴도 불필요해짐(Supabase Auth를
  안 쓰므로 `auth.users` 자체가 없음) — `users` 테이블에 `password_hash` 직접 저장
- **실시간(채팅/위치)**: Supabase Realtime 대신 **Spring WebSocket(STOMP)**으로 구현
  — v1 최초 계획이었던 `URLSessionWebSocketTask` 자체 서버 방향으로 사실상 회귀(단,
  서버는 Spring Boot)
- **배포**: 백엔드 서버는 지인 컴퓨터에서 24시간 상시 구동. CI/CD는 Git push 시 자동
  반영 — **자체 호스팅 GitHub Actions 러너**를 그 컴퓨터에 설치해 빌드/배포를 그
  머신에서 직접 수행하는 방식 권장(가정용 네트워크는 GitHub 클라우드 러너가 SSH로
  인바운드 접속하기 어려운 경우가 많아, 러너가 로컬에서 직접 도는 게 안전한 대안)
- **도메인/HTTPS**: iOS ATS 정책상 HTTPS 필수. 지인과 직접 협의 필요 — 상세는
  DEV_STACK_PIPELINE.md 및 ../TICKETS.md Q6 참조

이 결정으로 v1의 `URLSessionWebSocketTask` 계획은 사실상 부활(Realtime SDK 대체
계획은 폐기), ../design/DB_SCHEMA.sql·api/*는 Spring Boot 컨벤션으로 재작성됨.

## 7. 신규 아이디어 후보 (2026-07-19, 미확정): 반려동물 업체 연동 — 데일리 리포트

**아이디어 요약**: 강아지 유치원·미용실 등 업체가 PawWalk과 제휴하면, 견주가 앱에서 자기
반려견을 해당 업체에 "등록"할 수 있다. 업체 소속 직원(선생님)은 그날 맡은 반려견들의
일정, 사진, 특이사항을 앱을 통해 각 견주에게 공유한다. PawWalk은 참여 업체로부터
수수료(또는 구독료)를 받는다.

### 7.1 왜 좋은가
- **콜드스타트 우회 채널**: 기존 로드맵의 소셜 매칭·완료카드는 "동네에 친구가 이미
  좀 있어야" 가치가 생기는 구조라 초기 유저 밀도 문제가 크다(4장 참조). 반면 이 기능은
  유치원 **한 곳**만 계약해도 그 유치원 실고객(견주) 수십 명이 그대로 초기 유저가 된다 —
  소셜 코어와 완전히 다른, 독립적인 초기 획득 채널이 될 수 있다.
- **기존 케어 도메인과 자연스럽게 결합**: 예방접종 D-day, 건강 일지 등 이미 있는
  PET_CARE 영역과 같은 결을 공유한다. 다견종 등록 구조(Dog 엔티티)도 이미 있어 확장
  비용이 낮다.
- **업체를 광고주에서 진짜 파트너로 격상**: 4장 수익 모델에서 동물병원·펫샵·미용실·
  유치원은 이미 "타겟 광고" 대상으로 등장한다. 이 기능은 그 관계를 배너 광고 수준에서
  "일상적으로 앱을 켜게 만드는 핵심 사용 이유"로 끌어올린다 — 견주 입장에서 카카오톡
  단체방으로 받던 사진·특이사항을 앱 안에서 체계적으로(날짜별/반려견별) 보게 되는 것.

### 7.2 우려 및 트레이드오프
- **사업 성격이 다르다**: 지금까지의 PawWalk은 순수 B2C 소셜 앱이고, 이 기능은
  B2B2C(업체 영업 → 업체 직원 계정 → 견주)다. 업체 발굴·계약·정산이라는, 코드 작성과
  무관한 작업이 새로 생긴다. 1인 개발 + 학습 목적 프로젝트(4장 참조)라는 전제와
  맞는지는 별도 판단 필요 — "만들 수 있는가"와 "운영할 수 있는가"는 다른 문제.
- **업체 측 콜드스타트는 여전히 있다**: 유저 콜드스타트는 우회하지만, "제휴 업체를
  최소 1곳이라도 확보"라는 별도의 콜드스타트가 생긴다. 파일럿 업체 1곳을 어떻게
  구할지(지인 소개 등)가 실행 가능성을 가른다.
- **수수료 모델은 이미 한 번 기각된 전례가 있다**: 3장(v1)의 "산책 대행 수수료"는
  이번 v2에서 펫패스 선례(정확히 같은 C2C 수수료 모델로 서비스 종료)를 근거로 보류됐다.
  다만 이번 건은 C2C가 아니라 B2B2C라 구조가 다르므로 같은 리스크가 그대로 적용되진
  않지만, "수수료 정산·환불·과금 분쟁"이라는 운영 부담은 여전히 새로 생긴다는 점은
  동일하게 고려해야 한다.
- **인증/권한 설계가 필요**: 어떤 직원이 어떤 반려견에 리포트를 올릴 자격이 있는지
  검증하는 절차(견주 승인, 또는 업체가 발급한 등록 코드 입력 등)가 없으면 아무나
  타인의 반려견에 사진을 올릴 수 있는 상태가 된다 — 신뢰가 핵심인 기능이라 이 부분
  설계 전에는 착수하지 않는 게 안전하다.

### 7.3 필요한 신규 도메인(초안, 상세 설계 전)
- `Facility` — 제휴 업체(유치원/미용실 등), 업종 구분
- `FacilityStaff` — 업체 소속 직원 계정 (Member와 별도 role 또는 확장 필요)
- `DogEnrollment` — 반려견↔업체 연결(등록/승인 상태 포함)
- `DailyReport` — 반려견별 일일 리포트(일정, 사진, 특이사항), 작성자 = FacilityStaff

### 7.4 다음에 결정할 것
1. 온보딩 흐름 — 업체가 먼저 가입 신청하는지, 견주가 업체를 초대/등록하는지
2. 과금 방식 — 수수료(%) vs 정액 구독, 정산 주기와 결제 대행사(PG) 선정
3. 파일럿 업체 확보 전략 — 최소 1곳을 어떻게 섭외할지
4. 이 기능을 로드맵 Phase 몇에 둘지 — 소셜 코어(Phase 1~2)와 병행할지, 별도 트랙으로
   분리해 나중에 붙일지
