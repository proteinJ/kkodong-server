# 결정 기록 (Decision Log)

기획·설계 과정에서 **결론이 난** 항목과 그 근거다. 결론만이 아니라 **왜 그렇게
판단했는지**를 남기는 것이 목적이다 — 같은 논의를 반복하지 않기 위해서이고, 전제가
바뀌었을 때 어떤 결정을 다시 열어야 하는지 알기 위해서다.

아직 결론이 나지 않은 항목은 [`../TICKETS.md`](../TICKETS.md)의 **미결정 사항** 절에
해당 티켓과 함께 있다.

| # | 주제 | 결론 |
|---|---|---|
| D1 | 동물등록번호 API 실사 | 폐기 — 예방접종 이력을 제공하는 공공 API가 없다 |
| D2 | 성향·견종 매칭 알고리즘 도입 시점 | **Phase 1 핵심으로 격상** (v2에서 뒤집힘) |
| D3 | "유치원 대안" 카피의 안전 오해 리스크 | 조건부 확정 — 면책 문구는 출시 전 법률 자문 |
| D4 | 콜드스타트 지역 선정 | 우선순위 하락 — 반경 자동 확장이 문제를 흡수 |
| D5 | 신고·차단 기능 | Phase 1 포함 확정 |
| D6 | 성향 태그 세트 + 추천 가중치 초기값 | 확정 → [`RECOMMENDATION.md`](../design/RECOMMENDATION.md) |

> 원문은 `../TICKETS.md`(Q1~Q13)였다. 번호는 D1~D6으로 다시 붙였고, 미결정 항목

## D1. 동물등록번호 API 스펙 실사 — 완료

**배경**: ../archive/CONCEPT_v2.md에서 반려견 등록번호(동물등록제, 15자리) 기반
예방접종 알림 기능을 검토했다. 공공데이터포털에 "동물등록 정보조회 서비스" API가
존재하는 것은 확인됐으나(품종·생년월일·성별·중성화여부 등 기본 등록정보 반환),
**예방접종 이력까지 반환하는지는 검증되지 않았다**.

**조사 결과 (2026-07-08)**: 공공데이터포털 공식 페이지, 웹 검색, CODEF API 문서
세 출처 모두 일관되게 동물등록 정보조회 서비스(data.go.kr/data/15098913)의 응답
필드를 다음으로 한정한다 — 동물등록번호, RFID번호, 식별장치유형(내장/외장/인식표),
동물이름, 동물생년월일, 성별, 품종, 중성화여부, 관할기관, 등록일시. **예방접종/백신
관련 필드는 없음.** 국가동물보호정보시스템(animal.go.kr) 및 공공데이터포털 전체를
통틀어 예방접종 이력을 제공하는 별도 공공 API도 확인되지 않았다.

**결정**: 동물등록번호 API 연동으로 예방접종 이력을 가져오는 것은 **불가능** —
이 기능은 폐기한다. 예방접종/구충제 D-day 알림은 유저가 직접 입력한 접종일 기반으로만
구현한다 (../archive/CONCEPT_v1.md 2.4에 이미 정의된 방식 그대로 유지, 동물등록번호는
프로필 표시용 정보로만 남기고 API 연동은 하지 않음 — 저장하더라도 민감정보 최소화
원칙상 암호화 등 보안 설계는 별도 검토).

**상태**: 해결됨 — 등록번호 API 연동 폐기, 수동입력 기반 알림으로 확정

**출처**:
- [공공데이터포털 - 동물등록 정보조회 서비스](https://www.data.go.kr/data/15098913/openapi.do)
- [CODEF - 국가동물보호정보시스템 동물등록번호 조회 API](https://developer.codef.io/products/public/each/qa/animal/registration-number)

## D2. 성향/견종 매칭 알고리즘 도입 시점 — 🔄 v3에서 뒤집힘

> ### ⚠️ v3 갱신 (2026-08-15) — 아래 v2 내용보다 이 블록이 우선한다
>
> **결정 변경**: 성향·견종·나이 기반 강아지 친구 추천은 **HOLD가 아니라 이 플랫폼의
> 단 하나의 핵심 기능이며 Phase 1에 포함**된다(CONCEPT.md 2절). "유저 밀도
> 임계치 이후 재검토"라는 v2의 유예 결정은 폐기.
>
> **v2의 반대 근거는 어떻게 해소됐나**: v2가 HOLD한 이유는 알고리즘 자체가 아니라
> **"조건을 AND로 걸면 유효 후보군이 사라진다"**는 구조 문제였다. v3는 알고리즘 구조를
> 바꿔 이 문제를 없앤다 —
> - **하드 필터 금지, 가중치 랭킹만 사용** → 조건이 안 맞아도 후보에서 사라지지 않고
>   순위만 내려간다. 후보군이 0이 되는 경로 자체가 없다
> - **후보 부족 시 반경 자동 확장** → 화면이 항상 채워진다
> - 즉 "조건을 늘릴수록 풀이 좁아진다"는 전제가 성립하지 않는 설계다
>
> **해소되지 않은 근거**: 포동(DBTI 성향 데이터 보유)의 **카피 리스크는 그대로**다.
> v3의 방어선은 알고리즘이 아니라 누적된 산책 기록·친구 관계·카드 바이럴이라는
> 데이터/네트워크 자산이다(CONCEPT.md 7절 리스크 3).
>
> **"동네 반경 2km 월간 활성 50명" 임계치는?** 매칭 알고리즘 도입 트리거로서는
> 폐기(도입은 Phase 1 확정). 다만 **동네 밀도 지표 자체는 계속 추적**한다 — Q9(산책로
> 추천 활성화)와 Q8(지역 게이팅)의 판단 근거로 쓰인다.
>
> **관련 티켓**: FRIEND-1(추천 피드), FRIEND-2(신청/수락). 가중치 초기값은 **Q10**.
>
> ---
>
> *(이하 v2 원문 — 히스토리 보존용)*

**배경**: pm-strategist 검증(2026-07-08) 결과, "성향/견종 기반 강아지 친구 매칭"은
매칭 조건(성향+견종+반경)이 늘어날수록 유효 매칭 풀이 줄어들어 콜드 스타트를
오히려 악화시킨다는 판정(HOLD)을 받았다. 또한 포동이 이미 DBTI 성향 데이터를 보유하고
있어 PawWalk이 시장을 검증해주면 빠르게 카피당할 리스크도 있다.

**추가 맥락 (2026-07-08)**: 사용자가 유상 산책 대행은 하지 않을 확률이 높고, 플랫폼의
진짜 목적은 "강아지들끼리 친구를 만드는 것" 자체라고 명확히 함. 순수 로지스틱 매칭만으로는
이 목적을 충족하지 못한다는 판단 하에 절충안을 결정함.

**결정 (부분)**: 본격 다중조건 알고리즘(성향+견종+반경)은 계속 HOLD, Phase 3+로 유예.
대신 **MVP부터 유저 직접 입력 기반 심플 셀프 필터(크기/나이대/에너지레벨, 3개 이하)를
포함**하기로 결정 — 콜드 스타트를 크게 해치지 않으면서 "아무나 매칭"은 피하는 절충.

**임계치 결정 (2026-07-08, 잠정)**: 실측 데이터가 아직 없어 정밀한 값을 낼 수 없으므로,
Phase 1 출시 시점부터 추적할 지표와 잠정 임계치를 다음과 같이 정한다:
- 추적 지표: "동네(반경 2km) 월간 활성 유저 수" — Phase 1부터 대시보드/로그로 수집
- 잠정 재검토 트리거: 특정 동네 반경 2km 내 월간 활성 유저 **50명 이상**이 **연속 1개월**
  유지되는 시점 (성향+크기 등 다중조건 필터를 걸어도 유의미한 후보군이 남을 것으로
  추정되는 최소 규모 — 경험적 추정치이며, Phase 1 실제 매칭 성사율 데이터가 쌓이면
  재조정)
- Phase 1~2 기간 중 이 지표를 실제로 수집해 위 50명이라는 숫자가 타당한지 검증하고,
  Phase 3 진입 시점에 재확정

**상태**: 해결됨(잠정) — MVP 셀프 필터 확정 + 본격 알고리즘 재검토 트리거(동네 반경 2km
월간 활성 50명, 1개월 지속) 잠정 설정. Phase 1 실측 데이터로 재검증 예정

**⚠️ 단서 추가 (2026-07-08, 콜드스타트 검증)**: "50명·1개월"은 **실측 없는 확정
전제로 로드맵에 박아두면 안 된다.** pm-strategist 검증 결과 이 숫자를 광고 없이
오프라인 채널만으로 달성한 국내 반려동물 앱 사례를 찾지 못했다 — 근거가 약한
경험적 추정치임을 재확인. Phase 1 초기 4주간 퍼널(오프라인 접촉→설치→첫 산책 완료→
재방문) 전환율을 실측해서 이 숫자가 현실적인지 먼저 검증하고, 필요시 재조정한다.
상세: 아래 Q4.

## D3. "유치원 대안" 카피의 안전 오해 리스크 — 해결(조건부)

**배경**: 신규 포지셔닝 카피("유치원보다 저렴하게 산책 친구를 만드는 곳")는 페인포인트
서사로는 효과적이나, 실제 앱 기능은 훈련사 상주 감독이 있는 유치원과 달리 **보호자 간
자율 만남**이다. 이 차이를 명확히 하지 않으면 유저가 안전 수준을 오인하고, 물림 사고
등 발생 시 "유치원 대체재라며" 라는 신뢰 훼손 및 잠재적 법적 분쟁으로 이어질 수 있다.

**결정할 것**: 온보딩·이용약관·매칭 화면 등에 "본 서비스는 보호자 책임 하의 자율 만남을
중개하며, 유치원과 같은 전문가 감독을 제공하지 않는다"는 취지의 문구를 어디에, 어떤
톤으로 넣을지 정한다. 법률 자문이 필요한지도 함께 판단.

**초안 (2026-07-08)**: 아래 3개 지점에 배치하는 것으로 초안 확정, 문구는 TICKETS 작업 시
실제 UI 카피로 다듬는다:
1. **온보딩(최초 1회, 필수 동의 체크박스)**: "PawWalk은 보호자님들이 직접 만나 산책
   친구를 만드는 서비스예요. 훈련사가 상주하는 유치원과 달리 만남과 산책은 보호자님
   책임 하에 이루어집니다."
2. **매칭 상대 최초 만남 직전 화면(매번 노출)**: "처음 만나는 친구라면 안전한 장소에서,
   목줄을 유지한 채 짧게 인사부터 시작해보세요." (안전 수칙형 넛지, 매칭 성사 직후 1회성 경고보다 실질적 행동 유도가 목적)
3. **이용약관**: "회사는 보호자 간 만남을 중개할 뿐, 만남 중 발생하는 사고에 대해 직접적
   책임을 지지 않는다"는 취지의 면책 조항 — **이 조항은 법률 자문 필요 (정식 출시 전
   변호사 검토 필수, 기획 단계에서는 초안 방향만 확정)**

**상태**: 해결됨(카피 방향/배치 확정) — 단, 이용약관 면책조항 문구는 정식 출시 전 법률
자문 필요라는 조건부. ../TICKETS.md에 온보딩/매칭 화면 문구 티켓으로 반영

## D4. 콜드스타트 지역 선정 기준 + 오프라인 채널 실행 계획 — 🔄 v3에서 우선순위 하락

> ### ⚠️ v3 갱신 (2026-08-15)
>
> **하드 게이팅 결정은 Q8로 이관**됐다. v3의 반경 자동 확장(Q2 갱신 블록 참조)이
> "빈 매칭 결과로 인한 나쁜 첫인상"이라는 게이팅의 원래 명분을 상당 부분 흡수하기
> 때문이다. **ONBOARD-2 티켓은 Q8 결정 전까지 착수 보류.**
>
> **여전히 유효한 부분**: 후보 지역 숏리스트(이촌동/성수동/역삼·도곡동)와 **첫 4주
> 퍼널 실측 계획**은 v3에서도 그대로 유효하다. 지역을 *차단*하지 않더라도 **초기
> 오프라인 홍보를 어디에 집중할지**는 여전히 정해야 하고, 그 답이 이 숏리스트다.
> 즉 v3에서 이 항목은 "기능 게이팅 결정"에서 **"초기 마케팅 집중 지역 선정"**으로
> 성격이 바뀌었다.
>
> ---
>
> *(이하 v2 원문)*

**배경**: pm-strategist 콜드스타트 검증(2026-07-08) 결과, "지역을 좁혀서 시작한다"는
전략 방향(당근마켓 판교 사례 참고)은 GO이나, Q2에서 잠정 설정한 "동네 반경 2km 월간
활성 50명"을 **무예산 1인 개발로 실제 달성할 경로**는 검증되지 않았다(NO-GO 수준으로
근거 부족). 서울 구 단위 통계(반려견 등록수: 강남·송파·강서 순 / 가구 대비 비율:
용산 19.8%·강남 18.7%, 서울 평균 14.9% — [newsspace](https://www.newsspace.kr/news/article.html?no=2250))는
확인했으나, Q2가 요구하는 "반경 2km" 단위 밀집도(동 단위)는 확인하지 못했다.

**결정할 것**:
1. 구 전체가 아니라 **동/공원 반경 단위**로 후보지 2~3곳을 추리고, 반경 2km 내
   애견카페·동물병원·공원 개수를 직접 발품으로 실사해 최종 1곳을 선정
2. "50명·1개월" 목표를 한 번에 노리지 말고, **첫 4주간 퍼널 실측 계획**을 세운다
   (오프라인 접촉 수 → 설치 전환 → 첫 산책 완료 → 재방문 각 단계 전환율 기록)
3. 선정 지역 내 오프라인 채널(애견카페/병원/훈련소 리스트, 접촉 방법, 주당 투입
   가능 시간)을 1인 개발자 기준으로 현실적으로 견적

**후보 지역 숏리스트 (2026-07-08, 잠정 — 직접 답사 전)**: 구 단위 통계 + 알려진
반려견 인프라 밀집도 기준으로 좁힌 후보. 최종 선정은 여전히 직접 발품 답사 필요.
1. **용산구 이촌동** — 용산구 가구대비 반려견 비율 서울 1위(19.8%), 대단지 아파트
   + 한강공원 산책로 인접
2. **성동구 성수동(서울숲 인근)** — 서울숲이 반려견 산책 명소로 확인됨([반려생활](https://ban-life.com/content/view?id=93)),

3. **강남구 역삼동/도곡동** — 절대 반려견 마리수 서울 1위, 애견카페 인프라 확인.
   단 역삼동은 오피스 상권 성격이 강해 실거주 밀도는 이촌동보다 낮을 수 있음(미확인)

**서비스 지역 게이팅 방식 결정 (2026-07-08)**: "선정 지역만 먼저 연다"가 전체 유저

## D6. 성향 태그 세트 + 추천 알고리즘 가중치 초기값 — ✅ 해결 (2026-08-15)

**배경**: 친구 추천(FRIEND-1)이 핵심 기능인데, 그 입력값인 성향 태그가 정의되지
않았었다. 태그는 온보딩(ONBOARD-3)에서 입력받으므로 온보딩 구현 전에 확정돼야 하고,
나중에 바꾸면 기존 유저 전원 재입력이 필요하다.

**결정 (2026-08-15, 권장안대로 확정)**:

1. **성향 태그 세트** — **8개 중 최대 3개 선택**(0개 허용):
   활발함 / 차분함 / 사교적 / 낯가림 / 겁많음 / 장난꾸러기 / 독립적 / 애교많음
2. **가중치 초기값** — 거리 35 / 성격 25 / 나이 15 / 체급 15 / 견종 10,
   **성별·중성화는 0(미사용)**. 거리가 가장 높은 이유는 "만나러 갈 수 없으면 친구가
   되지 않기" 때문. 전부 `application.yml` 설정값으로 분리해 **재배포 없이 조정 가능**
3. **"궁합"의 정의** — **동일 성향 가산만.** 상보적 조합(활발+차분)에 가산점을 주지
   않는다 — 사람 기준 통념일 뿐 검증된 게 아니라서, 넣으면 추천이 나빠져도 알고리즘
   탓인지 가설 탓인지 분리할 수 없다
4. **추천 이유 문장** — 점수 숫자 대신 문장. **거리는 문장에서 제외**(후보 전원에게
   해당돼 정보가 없음), 성격 > 견종 > 나이 > 체급 순으로 최대 2개 절을 조합

**상세 명세**: **`../design/RECOMMENDATION.md`** — 점수 공식, 신호별 계산식,
견종 그룹 테이블, 문장 템플릿, 반경 확장 규칙, `application.yml` 설정 구조

**상태**: 해결됨 — ONBOARD-3 / PET-1 확장 / FRIEND-1 착수 가능

> ⚠️ **이 숫자들은 실측 없는 초기 추정치다.** 정확해서 고른 게 아니라 **조정 가능한
> 형태로 시작하려고** 고른 값이다. 검증 수단은 **친구 신청 수락률**뿐이며,
> **누적 신청 100건 이상**이 쌓이기 전에는 조정하지 않는다(소음에 반응한 튜닝 방지).
> 추적할 가설 5개는 ../design/RECOMMENDATION.md 4절.
>
> **남은 의존성**: `distance_score`의 정규화 기준이자 반경 확장 상한인
> `MAX_RADIUS_KM = 5`는 **Q8의 잠정값**이다. Q8이 다르게 결정되면 이 값도 함께 바뀐다.
