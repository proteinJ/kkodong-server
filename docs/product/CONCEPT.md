## 2. 핵심 기능 — 강아지 친구 찾기

**이 플랫폼의 존재 이유이자 단 하나의 핵심 기능.** 나머지 모든 기능(산책·커뮤니티·
카드·커머스·매장)은 이 핵심 루프를 지탱하거나 수익화하기 위한 주변부다. 기능 우선순위
충돌이 생기면 **친구 찾기에 기여하는 쪽을 택한다.**

### 2.1 추천 신호

주변 강아지를 다음 신호로 종합 평가해 추천한다.
**가중치 초기값은 2026-08-15 확정, 2026-08-27 개정** — 상세 계산식은
**`../design/RECOMMENDATION.md`**.

| 신호 | 가중치 | 출처 | 비고 |
|---|---|---|---|
| **거리** | **30** | `users.home_location` | 가장 높다 — 만나러 갈 수 없으면 친구가 안 된다 |
| **산책 시간대** | **15** ★ | 온보딩 선언값 `users.walk_time_slots` | 6개 중 최대 3개. **거리 논리를 시간축에 적용한 것** — 같은 동네여도 시간이 어긋나면 평생 안 마주친다 |
| **성격** | **20** | 온보딩에서 견주가 선택한 성향 태그 | 8개 중 최대 3개: 활발함/차분함/사교적/낯가림/겁많음/장난꾸러기/독립적/애교많음 |
| **나이** | **15** | `dogs.birth_date` | 개월수 차이 기반(36개월 차이면 0점) |
| **체급** | **12** | `dogs.size` | 안전(체급차 큰 만남의 사고 리스크) 반영 |
| **견종** | **8** | `dogs.breed` | 동일 견종 가산 + 견종 그룹 가산. **감점 신호로 쓰지 않는다** |
| 중성화·성별 | **0** | `dogs.neutered`, `dogs.gender` | **초기 미사용** — 어떤 조합이 더 나은지 근거가 없다. 컬럼만 유지하고 데이터를 보고 켠다 |

> **2026-08-27 개정 — 산책 시간대를 "데이터 쌓인 후"에서 초기 신호로 끌어올렸다.**
> 기존 판단은 산책 기록 누적을 기다리는 것이었으나, **온보딩 선언값으로 받으면 밀도
> 0에서도 즉시 작동한다**(성향 태그와 동일한 방식). 개친구가 실제로 생기는
> 메커니즘은 "성격이 맞아서"가 아니라 **"매일 같은 시간에 마주쳐서"** 이므로, 이
> 신호를 미루는 것이 가장 큰 설계 실수라고 판단했다. 합계 100 유지를 위해 거리
> 35→30, 성격 25→20, 체급 15→12, 견종 10→8로 조정. 근거: `MARKET.md` 4절 ①.
> 산책 기록이 쌓이면 선언값을 **실측으로 보정**한다(2단계).

**"궁합"은 동일 성향 가산만 인정한다.** 상보적 조합(활발함+차분함)에 가산점을 주지
않는다 — 사람 기준의 통념일 뿐 검증된 게 아니고, 넣으면 추천이 잘 안 될 때 알고리즘
탓인지 가설 탓인지 분리할 수 없어진다.

### 2.2 설계 원칙 — 하드 필터 금지, 가중치 랭킹

v2에서 성향/견종 매칭 알고리즘이 HOLD됐던 이유는 **"조건을 AND로 걸면 유효 후보군이
사라져 콜드스타트가 악화된다"**였다. v3에서는 이 문제를 알고리즘 구조 자체로 해결한다.

- **조건을 필터가 아니라 점수 가중치로 쓴다.** 성격이 안 맞아도 후보에서 사라지지
  않고 순위만 내려간다 → 후보군이 0이 되는 상황이 발생하지 않는다.
- **반경 자동 확장.** 기본 반경 내 후보가 최소 개수(N)에 못 미치면 반경을 단계적으로
  넓혀 항상 화면을 채운다. "주변에 아무도 없어요"는 최악의 첫인상이다.
- **점수를 유저에게 그대로 노출하지 않는다.** "궁합 87%" 같은 표기는 근거 없는
  정밀도를 주장하는 셈이고, 나중에 알고리즘을 바꾸기도 어려워진다. 대신 **"우리
  아이랑 나이도 비슷하고 둘 다 활발해요"** 처럼 **매칭 이유를 문장으로** 보여준다.
- **알고리즘 튜닝은 가중치 상수 조정으로 끝나야 한다** — 서버 설정값으로 빼두고
  실사용 데이터(친구 신청 수락률)로 조정한다.

### 2.3 친구 맺기 루프 (핵심 전환 퍼널)

```
① 주변 강아지 추천 피드
        │  (추천 이유 문장 + 강아지 누끼 프로필)
        ▼
② 친구 신청
        │
        ▼
③ 상대 견주 수락  ← 여기가 핵심 전환 지점. 수락률을 최우선 지표로 추적
        │
        ▼
④ 1:1 채팅 개설 (견주 ↔ 견주)
        │
        ▼
⑤ 다음 산책 약속 잡기 (시간·장소 제안 → 실제 만남)
        │
        ▼
⑥ 함께 산책 → 산책 완료 카드 → SNS 공유 → 신규 유입
```

⑤가 이 루프의 진짜 목적이다. 채팅만 하고 끝나면 실패 — **"약속 잡기"를 채팅 화면
안의 1급 기능으로 배치**한다(자유 채팅에 맡기지 않는다).

## 3. 기능 영역 전체

### 3.1 강아지 친구 찾기 ★핵심
2절 참조.

### 3.2 산책

- **산책 시작 / 종료** — GPS 기반 경로·거리·시간 기록
- **배변 기록**: 산책 중 화면의 **똥 / 오줌 아이콘**을 누르면 횟수가 기록된다.
  기록 시점의 위치·시각도 함께 저장 → 건강 지표(배변 빈도 변화)와 지도 표시로 확장 가능
- **지난 산책 경로 다시보기**: 저장된 경로를 지도에 다시 그려 보여줌. 마음에 든 경로는
  이름을 붙여 저장/즐겨찾기
- **동네 산책로 추천**: 우리 동네 강아지들이 실제로 걸었던 경로를 집계해 "산책하기
  좋은 길"을 추천
  - ⚠️ **밀도 의존 기능이다.** 동네에 산책 기록이 쌓이기 전에는 추천할 게 없다.
    초기에는 "내가 걸었던 경로" 재사용부터 열고, 동네 집계 추천은 해당 동네 산책
    세션이 임계치를 넘은 뒤 켜지는 **점진 활성화** 방식으로 간다(../TICKETS.md Q9)

### 3.3 산책 완료 카드 (바이럴 엔진)

- 산책 **종료 시점에 자동 생성** — 거리·시간·날씨·배변 횟수·강아지 누끼 사진 포함,
  인스타그램 스토리 규격(9:16)
- 인스타 등 SNS 공유용으로 설계 → **유료 광고 없이 신규 유입을 만드는 주력 채널**
- **카드 커스터마이징(템플릿·테마)은 패스권 유료 기능** (4절 수익 모델)

### 3.4 커뮤니티

- **자유 게시판** — 글 작성, 댓글, 좋아요. 주제 제한 없음(정보 공유·자랑·질문 등)
- 산책 기록 피드와 별개의 독립 탭
- ⚠️ v2에서 "포동(44만+ 가입자)과 정면충돌"을 이유로 NO-GO였던 항목이 **v3에서
  되살아났다**(7절). 차별화는 커뮤니티 자체가 아니라 **"친구 맺은 강아지들이 모여 있는
  동네 커뮤니티"라는 맥락**에서 나온다 — 동네/친구 기반 노출 우선순위를 반드시 넣는다

### 3.5 강아지 누끼 (배경 제거)

- **가입 온보딩에서 강아지 사진을 찍으면 배경이 제거된 "누끼 사진"이 자동 생성**된다
- 이 누끼 이미지가 **프로필과 산책 카드에 일관되게 쓰이는 시각적 아이덴티티**
- 기술: iOS Vision `VNGenerateForegroundInstanceMaskRequest` (온디바이스, 서버 비용 0)
- ⚠️ v2에서는 "아이폰 기본 사진 앱도 되는 기능이라 차별화 약함"으로 저우선이었으나,
  v3에서는 **차별화 기술이 아니라 온보딩·카드·프로필을 관통하는 브랜드 자산**으로
  역할이 바뀌었다. Phase 1 포함

### 3.6 반려견 케어 알림

입양 직후 견주가 가장 헤매는 지점을 잡는 부가 기능.

| 항목 | 주기 예시 |
|---|---|
| 예방접종 | 종합백신 1차~5차, 광견병 등 (차수·간격 관리) |
| 심장사상충 예방약 | 월 1회 반복 |
| 구충제 | 주기 반복 |
| 건강검진 | 연 1회 등 |

- **입력 방식은 유저 수동 입력** — 동물등록번호 API는 예방접종 이력을 반환하지 않음이
  확인되어 연동 폐기(../TICKETS.md Q1, 변경 없음)
- 견종·나이 기반 **기본 스케줄 템플릿을 앱이 제시**하고 유저가 실제 접종일만 입력하면
  다음 차수 D-day가 자동 계산되는 방식
- 알림: 로컬 알림(`UNUserNotificationCenter`) + 원격 푸시(APNs)

### 3.7 매장 지도 & 리뷰 (플랫폼 확장)

- 지도에서 **반려견 관련 매장**(동물병원, 미용실, 애견카페, 유치원, 훈련소, 호텔,
  펫샵 등) 확인 및 검색
- 견주가 **평점·리뷰** 작성 → 매장 신뢰도 형성
- 지도에 뜨는 매장 정보의 원천은 **점주 전용 앱에서 점주가 직접 등록한 데이터**(3.9)

### 3.8 예약

- 꼬동을 통해 매장에 **사전 예약**
- **등록된 반려견 정보(견종·체중·나이·중성화·접종 이력 등)가 예약에 자동으로 실려
  전달**된다 → 견주는 매번 설명할 필요가 없고, 점주는 미리 준비할 수 있다.
  **이것이 단순 예약 앱과의 차별점이며, 매장이 꼬동을 쓸 이유 그 자체다**
- 예약 확정/변경/취소 알림은 양쪽 앱에 푸시

### 3.9 꼬동 파트너 — 점주 전용 앱

| 기능 | 설명 |
|---|---|
| 매장 등록 | 등록하면 꼬동(견주 앱) 지도에 노출 |
| 예약 관리 | 들어온 예약 확인/승인/거절, 캘린더 |
| 홍보 | 매장 소식·이벤트·쿠폰 게시 |
| 리뷰 관리 | 견주 리뷰 확인 및 답글 |
| 고객(반려견) 정보 조회 | 예약과 함께 전달된 반려견 정보 열람 |

⚠️ **B2B2C 사업 성격이 새로 생긴다.** 매장 발굴·계약·정산·CS는 코드 작성과 무관한
운영 업무다. 1인 개발 전제와의 정합성은 ../TICKETS.md Q11에서 계속 추적한다.

### 3.10 커머스 — 반려견 용품 직접 판매 + 콘텐츠 상품 태그

**2026-08-22 모델 전환**: 중개(마켓플레이스)가 아니라 **꼬동이 직접 매입해 파는 1P
커머스**다. 판매자는 꼬동 하나뿐이고, 유저는 구매자이자 콘텐츠 생산자 역할만 한다.

**콘텐츠 → 구매 동선** (오늘의집 모델의 핵심):

```
유저가 강아지 보금자리·생활 환경 사진을 올린다
        │  사진 속 물건에 꼬동 카탈로그 상품을 태그 (자사 상품으로만 제한)
        ▼
다른 유저가 사진을 구경하다 태그를 눌러 상품 상세로 이동
        ▼
구매 → 리뷰 작성 → 그 리뷰가 다시 다음 구매를 만든다
```

**"서로 강아지 집을 자랑하는 것"이 곧 판매 동선**이다. 광고비 없이 상품 노출이
일어나는 구조이고, 커뮤니티 체류시간이 그대로 매출로 연결된다.

- 수익: **판매 마진** (중개 수수료 아님)
- 태그 대상은 **자사 카탈로그로 제한** — 가짜 판매자·가짜 상품이 원천적으로 불가능하고,
  결제 경로가 플랫폼 하나뿐이라 사칭의 금전적 동기가 사라진다(6절 안전·신뢰와 연결)
- 연결 고리: 산책 카드·케어 알림·매장 리뷰에서 상품으로 이어지는 동선은 그대로 유지
  (예: 심장사상충약 D-day 알림 → 관련 상품, 산책 기록 → 하네스/리드줄)

⚠️ **직접 판매의 대가**: 중개에는 없던 **재고 매입 자금·물류(입고/포장/배송)·
반품/교환/불량 CS**가 전부 운영자 몫이 된다. 판매자 확보라는 콜드스타트는 사라지지만,
1인 운영 부담은 중개보다 훨씬 크다 — 7절 리스크 1번과 ../TICKETS.md Q11·Q12에서 계속 추적한다.

⚠️ **창작자 보상을 붙일 경우**: "내 사진에 태그된 상품이 팔리면 적립금" 같은 리워드를
넣으면 **사진 도용이 수익성 있는 공격**이 된다(남의 사진을 퍼와 태그 → 적립금 수령).
리워드를 넣지 않으면 이 위험은 발생하지 않는다. 넣는다면 이미지 중복 탐지·지급 유예·
계정 이력 요건이 함께 필요하다.

## 4. 수익 모델

| 축 | 내용 | 작동 시점 |
|---|---|---|
| **① 패스권(구독)** | 강아지 **추가 등록** 권한 + **산책 카드 커스터마이징** 권한 | **초기부터** — 유저 밀도와 무관하게 작동하는 유일한 축 |
| **② 커머스 판매 마진** | 반려견 용품 **직접 판매(1P)** + 콘텐츠 상품 태그 동선 | 중기 — 상품 소싱·물류 준비 후 |
| **③ 매장(파트너) 수익** | 예약 수수료 또는 점주 정액 구독 + 지도 상단 노출 광고 | 중기 — 매장 확보 후 |
| **④ 타겟 광고** | 동네 단위 반려동물 업체 광고 | 후행 — 유저 밀도가 쌓인 뒤 |

**전환 설계 원칙(v1부터 유지)**: 기능적 제한이 아니라 **감성적으로 의미 있는
행동**(내 강아지 한 마리 더 등록하기, 우리 아이 카드 예쁘게 꾸미기)에 락온을 건다.
저항감이 낮고 전환율이 높다.

**핵심 루프는 끝까지 무료다.** 친구 찾기·산책 기록·기본 카드·커뮤니티에는 과금하지
않는다(당근마켓 벤치마킹, v2 4절 원칙 유지). 여기에 과금하면 밀도가 죽고, 밀도가
죽으면 ②③④가 전부 무너진다.

**초기 현금흐름 원칙(v2 유지)**: 인프라를 트래픽 연동형으로 설계해 매출 0에서도 고정비가
거의 들지 않게 하고, 패스권만 MVP부터 켜둔다.

## 5. 로드맵

**Phase 1 범위 결정(2026-08-15)**: 핵심 루프에 집중 — 친구찾기 + 산책 + 카드 +
커뮤니티. 매장·예약·커머스·점주앱은 Phase 2 이후로 분리.

| Phase | 목표 | 포함 |
|---|---|---|
| **Phase 1 — 핵심 루프** | 강아지 친구가 실제로 생기는가 | 인증/온보딩, **누끼 프로필**, 반려견 등록, **친구 추천→신청→수락**, 1:1 채팅 + **산책 약속**, 산책 기록 + **배변 기록**, 지난 경로 다시보기, **산책 완료 카드 + SNS 공유**, **자유 커뮤니티**, 케어 알림, 차단/신고, 패스권 |
| **Phase 2 — 동네 밀도** | 동네 데이터가 가치를 만드는가 | **동네 인기 산책로 추천**, 그룹 산책, 다인 완료 카드, 카드 커스터마이징 확대, 커뮤니티 동네/친구 기반 랭킹 |
| **Phase 3 — 매장 생태계** | 점주가 들어오는가 | **매장 지도·검색·리뷰**, **꼬동 파트너(점주 앱)**, **예약 시스템(반려견 정보 자동 전달)** |
| **Phase 4 — 커머스** | 거래가 도는가 | 용품 **직접 판매(1P)**, 보금자리 사진 + **상품 태그**, 구매 리뷰, 상품 추천 동선, 타겟 광고 |

**Phase 순서의 근거**: 매장(Phase 3)은 "견주가 이미 거기 모여 있어야" 점주가 들어올
이유가 생긴다. 커머스(Phase 4)는 직접 판매로 바뀌어 판매자 확보 문제는 없어졌지만,
**콘텐츠(보금자리 사진)를 올릴 유저가 이미 모여 있어야** 태그 동선이 작동한다. 즉 **Phase 1의
핵심 루프가 실패하면 3·4는 시작조차 불가능하다** — 순서를 뒤집지 않는다.

## 7. v2 대비 뒤집힌 결정 (중요)

새 기획은 v2에서 HOLD/NO-GO였던 항목들을 다수 되살린다. **의도된 방향 전환이며,
각 항목의 원래 반대 근거는 사라진 게 아니므로 완화책을 함께 명시한다.**

| 항목 | v2 판정 | v3 | 원래 반대 근거 | v3의 완화책 |
|---|---|---|---|---|
| 성향/견종 매칭 알고리즘 | HOLD (Phase 3+) | **핵심 기능, Phase 1** | 조건 AND로 후보군 소멸 → 콜드스타트 악화 / 포동 DBTI 카피 리스크 | **하드 필터 폐지, 가중치 랭킹 + 반경 자동 확장**(2.2)으로 후보군 0 상황 원천 차단 |
| 범용 커뮤니티 | NO-GO | **Phase 1 포함** | 포동(44만+)과 정면충돌 | 범용 커뮤니티가 아니라 **동네·친구 맥락 기반** 노출 우선순위로 차별화(3.4) |
| 시설(매장) 탐색 | HOLD | **Phase 3 핵심 축** | 비마이펫 등 레드오션 | 단순 정보 나열이 아니라 **점주앱 + 반려견 정보 자동 전달 예약**으로 결합(3.8) — 정보 앱이 아니라 예약 인프라 |
| 누끼 프로필 | Phase 2, 저우선 | **Phase 1** | iPhone 기본 기능과 체감차 적음 | 차별화 기술이 아니라 **온보딩→프로필→카드를 관통하는 브랜드 자산**으로 역할 재정의 |

| 서비스 지역 게이팅 | Phase 1 필수(ONBOARD-2) | **완화 — 게이팅 유지하되 전국 오픈 기본** | 빈 매칭 결과로 인한 나쁜 첫인상 | 반경 자동 확장(2.2)이 "후보 0" 문제를 상당 부분 흡수하므로 하드 게이팅 필요성 감소. 상세: ../TICKETS.md Q8 |

### 계속 유지되는 결정 (변경 없음)

- **유상 산책 대행: 폐기 유지** — 펫패스 선례(동일 모델로 서비스 종료) + 배상책임/CS가
  1인 개발 범위 초과. 새 기획에도 언급 없음
- **동물등록번호 API 연동: 폐기 유지** — 예방접종 이력 미반환(Q1)
- **백엔드 아키텍처: Spring Boot 자체 서버 + Supabase Postgres 호스팅** (../archive/DEV_STACK_PIPELINE.md)
- **핵심 루프 무료 유지 원칙**

### ⚠️ 남는 리스크 (해소되지 않음, 계속 관리 대상)

1. **범위 폭증 대비 1인 개발 리소스** — v3는 사실상 4개 사업(소셜/커머스/O2O 예약/
   광고)을 하나에 얹은 구조다. Phase 1 범위를 핵심 루프로 좁힌 것이 유일한 방어선이므로
   **Phase 1이 끝나기 전에 Phase 3~4 기능을 앞당기지 않는다.**
   ⚠️ 2026-08-22 커머스가 직접 판매로 바뀌면서 이 리스크는 **더 커졌다** — 코드가 아니라
   재고·물류·반품이라는 물리적 운영이 붙는다. Phase 4 착수 전에 위탁배송(3PL) 등으로
   운영 부담을 줄일 방법을 먼저 정할 것.
2. **양면시장이 두 개** — ①견주↔견주(친구), ②견주↔점주(예약). 각각 독립적인
   콜드스타트를 갖는다. Phase를 분리한 이유가 이것이다.
3. **포동 카피 리스크는 여전히 존재** — 성향 데이터를 이미 보유한 경쟁자가 친구 추천을
   따라올 수 있다. 방어선은 알고리즘이 아니라 **누적된 산책 기록·친구 관계·카드
   바이럴**이라는 데이터/네트워크 자산이다.
