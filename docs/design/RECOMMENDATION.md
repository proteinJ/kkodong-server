## 1. 성향 태그 세트 (확정)

| 태그 | |
|---|---|
| 활발함 | 차분함 |
| 사교적 | 낯가림 |
| 겁많음 | 장난꾸러기 |
| 독립적 | 애교많음 |

- **총 8개, 견주가 최대 3개까지 선택.** 필수 아님(0개도 허용)
- 입력 시점: 온보딩(ONBOARD-3) 강아지 등록 화면. 이후 프로필에서 수정 가능
- 저장: `dogs.personality_traits` JSONB 배열 (예: `["활발함","사교적"]`)

**8개·최대 3개인 이유**: 태그가 많으면 선택 부담이 커지고 겹치는 태그가 줄어 매칭
신호가 희석된다. 반대로 너무 적으면 변별력이 없다. 3개 제한은 "우리 아이를 한 마디로
표현하기"에 가까운 부담이면서, 두 강아지가 우연히 겹칠 확률도 충분히 남긴다.

### 검증 규칙
- **개수 제한(≤3)은 DTO `@Size` + DB CHECK 제약**(`chk_dogs_personality_traits`)으로 —
  안정적이고 바뀔 일이 적다
- **태그 값 유효성은 서버 설정값**(`kkodong.dog.personality.tags`)으로 — enum이 아니다.
  태그 세트는 실사용 데이터에 따라 바뀔 수 있으므로 DB 제약이나 코드에 문자열을
  박아두면 변경할 때마다 마이그레이션·재배포가 필요해진다. 위반 시 400 `D004`

### ⚠️ 이 태그 세트의 알려진 약점 (데이터로 확인할 것)
1. **의미가 겹치는 태그가 있다** — `낯가림`↔`겁많음`, `활발함`↔`장난꾸러기`.
   실제로 항상 같이 선택된다면 둘 중 하나를 없애 태그를 7개로 줄인다
2. **`낯가림`/`겁많음`은 "사교성 낮음" 신호다.** 아래 3절의 동일 성향 가산 규칙에 따르면
   낯가리는 강아지끼리 서로 상위에 추천된다. 이게 좋은 매칭인지는 **검증되지 않았다** —
   4절의 추적 가설 #1

## 2. 점수 공식

후보군은 **반경 조건으로만** 좁히고, 나머지는 전부 정렬 가중치다
(하드 필터 금지 — `../product/CONCEPT.md` 2.2).

```
score = 30 × distance_score
      + 15 × time_slot_score      ★ 2026-08-27 신설
      + 20 × personality_score
      + 15 × age_score
      + 12 × size_score
      +  8 × breed_score
```

각 `*_score`는 **0.0 ~ 1.0**으로 정규화되고, 가중치 합은 100이다(읽기 쉬우라고).

### 가중치 초기값과 근거

| 신호 | 가중치 | 왜 이 값인가 |
|---|---|---|
| 거리 | **30** | 가장 높다. 성격이 아무리 맞아도 **만나러 갈 수 없으면 친구가 안 된다.** 이 제품의 목적은 채팅이 아니라 실제 만남이다 |
| **시간대** | **15** ★ | **거리 논리를 시간축에 그대로 적용한 것.** 같은 동네여도 나는 새벽 6시, 상대는 밤 11시면 평생 안 마주친다. 개친구가 실제로 생기는 메커니즘은 "성격이 맞아서"가 아니라 **"매일 저녁 8시에 같은 데서 마주쳐서"** 다 |
| 성격 | **20** | 핵심 차별 신호. 다만 **자기 신고(self-report) 데이터**라 정확도에 한계가 있어 거리보다 낮게 둔다 |
| 나이 | **15** | 또래일수록 놀이 방식·체력이 맞을 가능성 |
| 체급 | **12** | **안전 요소**이기도 하다 — 체급 차가 큰 만남은 사고 위험이 있다 |
| 견종 | **8** | 가장 낮다. 견주에게 "같은 견종"은 반가운 신호지만, 견종이 다르다고 못 노는 건 아니다. **감점이 아니라 가산 신호**로만 쓴다 |
| 성별·중성화 | **0 (미사용)** | 아래 참조 |

> **2026-08-27 개정** — 시간대 15점을 신설하고 합계 100을 유지하기 위해 거리 35→30,
> 성격 25→20, 체급 15→12, 견종 10→8로 조정했다. 근거는
> [`../product/MARKET.md`](../product/MARKET.md) 4절 ①·②.
>
> ⚠️ **시간대를 "데이터 쌓인 후"로 미루지 않는 이유**: 온보딩 선언값으로 받으면
> 밀도 0에서도 즉시 작동한다. 성향 태그와 정확히 같은 방식이다.

**성별·중성화를 0으로 두는 이유**: `../product/CONCEPT.md` 2.1에 "보조 신호"로 적혀
있지만, **어떤 조합이 더 좋은 매칭인지에 대한 근거가 없다.** 근거 없는 가중치를 넣으면
추천 품질이 나빠져도 원인을 분리할 수 없다. 컬럼은 유지하되 초기 가중치는 0으로 두고,
필요해지면 데이터를 보고 켠다. (중성화되지 않은 이성 조합 회피 같은 규칙은 실제 견주
니즈를 확인한 뒤 검토 — 4절 가설 #4)

### 각 신호의 계산

**거리 — `distance_score`**
```
distance_score = max(0, 1 − distance_km / MAX_RADIUS_KM)
```
- `MAX_RADIUS_KM = 5` (반경 자동 확장 상한, ../TICKETS.md Q8 잠정값)
- 0km → 1.0 / 2.5km → 0.5 / 5km 이상 → 0.0
- ⚠️ **현재 반경이 아니라 고정 상한으로 나눈다.** 반경이 확장될 때마다 기준이 바뀌면
  같은 상대의 점수가 조회할 때마다 달라진다

**성격 — `personality_score`**
```
shared = |A ∩ B|                       (겹치는 태그 개수)
personality_score = shared / min(|A|, |B|)
```
- 한쪽이라도 태그가 0개면 → **0.5 (중립)**
- ⚠️ **태그 미입력을 0점으로 처리하면 안 된다.** 온보딩에서 태그를 건너뛴 신규 유저가
  영원히 추천 하위에 깔려 아무에게도 안 보이게 된다 — 콜드스타트를 스스로 만드는 셈

**나이 — `age_score`**
```
age_score = max(0, 1 − |개월수A − 개월수B| / 36)
```
- 36개월(3년) 이상 차이 → 0.0 / 동갑 → 1.0
- 생년월일 미입력 → **0.5 (중립)**

**체급 — `size_score`**

| 체급 차이 | 점수 |
|---|---|
| 같음 (small↔small 등) | 1.0 |
| 한 단계 (small↔medium) | 0.5 |
| 두 단계 (small↔large) | 0.0 |

- 미입력 → **0.5 (중립)**

**견종 — `breed_score`**

| 관계 | 점수 |
|---|---|
| 완전히 같은 견종 | 1.0 |
| 같은 견종 그룹 | 0.6 |
| 다른 그룹 | **0.2** |
| 한쪽이라도 미입력·믹스 | 0.3 |

- ⚠️ **다른 그룹이 0.0이 아닌 이유**: 견종이 다른 건 감점 사유가 아니다. 0으로 두면
  견종이 사실상 배제 필터처럼 작동한다
- **믹스견을 "같은 견종"으로 묶지 않는다** — 믹스끼리 유사하다는 근거가 없고, 국내
  비중이 커서 잘못 묶으면 매칭 품질이 크게 흔들린다

**견종 그룹 초기 테이블** (서버 설정, 자유롭게 확장):

| 그룹 | 견종 |
|---|---|
| `small_companion` 소형 반려견 | 말티즈, 포메라니안, 치와와, 시츄, 요크셔테리어, 비숑프리제, 토이푸들, 페키니즈, 파피용 |
| `terrier` 테리어 | 잭러셀테리어, 미니어처슈나우저, 웨스트하이랜드화이트테리어, 폭스테리어 |
| `sporting` 사냥·스포팅 | 비글, 코커스패니얼, 골든리트리버, 래브라도리트리버, 닥스훈트 |
| `herding` 목축·사역 | 웰시코기, 보더콜리, 셰퍼드, 사모예드, 허스키 |
| `korean` 한국 견종 | 진돗개, 삽살개, 풍산개 |
| `other` 기타 | 위 목록에 없는 견종 |
| `mixed` 믹스 | 믹스견 — **그룹 매칭에서 제외**(항상 0.3) |

> **한 견종은 정확히 한 그룹에만 넣는다.** 예컨대 포메라니안은 스피츠 계열이지만
> 국내에서는 소형 반려견으로 인식되므로 `small_companion`에만 둔다 — 이 표의 목표는
> 견종학적 정확성이 아니라 **"견주가 보기에 비슷한 종류"**다.
>
> `other`끼리는 같은 그룹으로 치지 않는다(0.2 적용). "분류가 안 된 견종"이라는 이유로
> 서로 비슷하다고 볼 근거가 없다.
>
> 서버 설정 파일로 관리해 코드 수정 없이 고칠 수 있게 한다.

**산책 시간대 — `time_slot_score`** ★ 2026-08-27 신설

온보딩에서 **6개 슬롯 중 최대 3개**를 고르게 한다(성향 태그와 동일한 방식, 건너뛰기 허용).

| 슬롯 키 | 표시 | 비고 |
|---|---|---|
| `dawn` | 새벽 (05~08) | |
| `morning` | 아침 (08~11) | 출근 전 산책 |
| `noon` | 낮 (11~15) | 여름철엔 노면 온도로 기피 |
| `afternoon` | 오후 (15~18) | |
| `evening` | 저녁 (18~21) | **최대 피크** |
| `night` | 밤 (21~24) | |

```
겹침 = |내 슬롯 ∩ 상대 슬롯|
time_slot_score = 겹침 / min(|내 슬롯|, |상대 슬롯|)

한쪽이라도 미입력 → NEUTRAL(0.5)
```

⚠️ **자카드(합집합 분모)를 쓰지 않는 이유.** 내가 `저녁`만 고르고 상대가
`아침·저녁`을 골랐다면 우리는 **실제로 저녁에 만날 수 있다.** 자카드는 이를
1/2 = 0.5로 깎지만, 우리가 재려는 것은 "취향이 얼마나 같은가"가 아니라
**"마주칠 수 있는가"** 다. 그래서 최솟값을 분모로 하는 중첩계수를 쓴다.

⚠️ **최대 3개 제한이 이 공식의 전제다.** 상한이 없으면 6개를 전부 고른 유저가
모두와 1.0으로 겹쳐 상위를 독식한다. 개수 제한은 **DB CHECK 제약**으로 걸어
성향 태그와 동일하게 방어한다.

**2단계 — 선언값을 실측으로 보정** *(WALK 착수 후)*

산책 기록이 쌓이면 실제 시작 시각 분포로 선언값을 덮어쓴다. 사람은 자기 습관을
부정확하게 신고하며(특히 "새벽에 걷는다"고 답하고 실제로는 아침에 걷는다),
실측이 있으면 그쪽이 언제나 낫다. 선언값은 콜드스타트 발판으로 남는다.

### 동점 처리 — 무작위 셔플 (중요)

점수가 완전히 결정적이면 **상위에 뜬 강아지가 응답하지 않아도 계속 상위에 남아**
추천 화면이 정체된다.

```
1. score를 소수점 첫째 자리에서 반올림
2. 같은 점수 그룹 안에서 무작위 셔플
3. 시드 = f(내 user_id, 오늘 날짜)  ← 같은 날 새로고침하면 순서가 같고, 날이 바뀌면 달라진다
```

> 노출 이력 기반 감점(본 적 있는데 신청 안 한 상대 하향)은 별도 노출 로그 테이블이
> 필요하다. **Phase 1 범위 밖** — 위 셔플로 대신한다.

## 3. "궁합"의 정의 — 동일 성향 가산만 (확정)

성격 점수는 **겹치는 태그가 많을수록 높다.** 상보적 조합(활발함 + 차분함)에 가산점을
주지 않는다.

**이유**: "활발한 아이에겐 차분한 친구가 좋다"는 건 **사람 기준의 통념이지 검증된
사실이 아니다.** 근거 없는 규칙을 초기값에 넣으면, 추천이 잘 안 될 때 그게 알고리즘
탓인지 가설 탓인지 분리할 수 없다. 검증 가능한 가장 단순한 가설(같으면 잘 맞는다)로
시작해 데이터로 반증한다.

## 4. 추적할 가설 (Phase 1 데이터로 검증)

측정 지표는 전부 **친구 신청 수락률**(= 수락 수 / 신청 수)로 통일한다.

| # | 가설 | 반증되면 |
|---|---|---|
| 1 | **낯가림·겁많음 태그끼리의 매칭도 다른 조합만큼 수락된다** | 해당 태그는 동일 가산에서 제외하거나 가중치를 낮춘다 |
| 2 | 거리 가중치 30이 적절하다 | 먼 거리 매칭의 **약속 성사율**(CHAT-2)이 낮으면 거리 가중치를 올린다 |
| 3 | 성격 겹침이 수락률을 실제로 올린다 | 상관이 없으면 성격 가중치를 낮추고 거리·나이로 재배분 |
| 4 | 성별·중성화는 매칭 품질과 무관하다 | 유의미하면 가중치를 켠다 |
| 5 | 8개 태그가 서로 구별된다 | 항상 같이 선택되는 쌍이 있으면 태그를 병합/삭제 |

**최소 관측 규모**: 신청 표본이 적으면 어떤 결론도 낼 수 없다. **누적 친구 신청
100건 이상**이 쌓이기 전에는 가중치를 조정하지 않는다 — 소음에 반응해 튜닝하면
알고리즘이 더 나빠진다.

## 5. 추천 이유 문장 (`reason`)

**점수를 숫자로 노출하지 않는다.** ("궁합 87%" 금지 — 근거 없는 정밀도를 주장하게
되고, 나중에 알고리즘을 바꾸기도 어려워진다.) 대신 서버가 문장을 만들어 내려준다.

### 생성 규칙

```
1. 거리를 제외한 5개 신호(시간대/성격/나이/체급/견종) 중 임계치를 넘은 것만 후보로 모은다
2. 후보를 우선순위대로 정렬: **시간대 > 성격 > 견종 > 나이 > 체급**
3. 상위 최대 2개를 골라 문장으로 조합한다
4. 후보가 하나도 없으면 → 거리 fallback 문장을 쓴다
```

**거리를 문장에서 빼는 이유**: 점수에서는 가장 중요하지만, "가까워요"는 추천 이유로서
정보가 없다. 후보 전원에게 해당되기 때문이다.

**시간대를 1순위로 두는 이유**: 유일하게 **즉시 행동으로 이어지는** 정보다.
"둘 다 활발해요"는 감상이지만 "저녁에 산책하는 것도 같아요"는 **오늘 저녁에 나가볼
이유**가 된다. 이 제품의 목적이 채팅이 아니라 실제 만남이라는 점과 정확히 일치한다.

### 절(clause) 템플릿

| 신호 | 조건 | 문구 |
|---|---|---|
| **시간대** | 겹치는 슬롯 있음 | `{슬롯 표시}에 산책하는 것도 같아요` |
| 성격 | 겹치는 태그 2개 이상 | `{태그1}·{태그2}한 성격이 우리 아이랑 닮았어요` |
| 성격 | 겹치는 태그 1개 | `둘 다 {태그1} 성격이에요` |
| 견종 | 같은 견종 | `우리 아이랑 같은 {견종}이에요` |
| 견종 | 같은 그룹 | `우리 아이랑 비슷한 종류예요` |
| 나이 | 6개월 이내 | `나이가 거의 같아요` |
| 나이 | 18개월 이내 | `나이가 비슷해요` |
| 체급 | 같은 체급 | `체급이 비슷해서 같이 놀기 좋아요` |
| 거리(fallback) | 1km 이내 | `걸어서 만날 수 있는 거리예요` |
| 거리(fallback) | 그 외 | `우리 동네 가까이 사는 친구예요` |

### 조합

- 2개면 `", "`로 잇는다 → `"둘 다 활발한 성격이에요, 나이도 비슷해요"`
- 1개면 그대로
- 태그 이름은 **어미를 다듬어 넣는다**(`활발함` → `활발한`). 서버에 태그별 표시형
  문자열을 함께 둘 것 — 문자열 조작으로 처리하지 말 것

### 예시

| 상황 | 결과 |
|---|---|
| 시간대 겹침 + 태그 2개 겹침 | `저녁에 산책하는 것도 같아요, 활발·사교적인 성격이 우리 아이랑 닮았어요` |
| 태그 2개 겹침 + 동갑 | `활발·사교적인 성격이 우리 아이랑 닮았어요, 나이가 거의 같아요` |
| 같은 견종 + 같은 체급 | `우리 아이랑 같은 말티즈예요, 체급이 비슷해서 같이 놀기 좋아요` |
| 겹치는 신호 없음, 800m | `걸어서 만날 수 있는 거리예요` |

## 6. 후보 조회 & 반경 확장

```sql
SELECT d.*, u.id AS owner_id
FROM dogs d
JOIN users u ON u.id = d.owner_id
WHERE u.id <> :me
  AND ST_DWithin(u.home_location,
                 ST_SetSRID(ST_MakePoint(:lng, :lat), 4326)::geography,
                 :radius_m)
  AND d.id NOT IN (:blocked_or_friend_or_pending)
ORDER BY <score> DESC
LIMIT :limit
```

### ⚠️ 후보 풀 상한은 요청 `limit`과 별개다 (2026-09-07 추가)

위 쿼리의 `LIMIT`에 요청 `limit`(응답 개수)을 넣으면 **거리가 하드 필터가 된다.**
가장 가까운 20마리만 뽑아서 그 안에서 재정렬하는 것이므로, 나머지 5개 신호는
**이미 거리로 걸러진 집합의 순서만** 바꾸게 된다 — 2절 "필수 설계 제약" 1번 위반이다.

**반경 안에서는 거리의 변별력이 가장 낮다.** 반경 확장은 후보가 `limit` 이상 나오는
첫 단계에서 멈추므로, 밀집 지역이면 1km에서 확정된다. 그 안에서 각 신호의 점수 폭은:

| 신호 | 1km 안에서의 점수 폭 |
|---|---|
| 거리 | **6점** (0km 30 → 1km 24) |
| 성격 | 20점 |
| 시간대 | 15점 |

> 1km 안에 300마리가 있으면 20번째로 가까운 개는 약 258m에 있다. 260m의 "시간대·성격이
> 완벽히 맞는 개"는 120m의 "아무것도 안 맞는 개"에게 **거리 0.9점 차로 밀려** 후보에서
> 잘린다. 점수로는 34점을 이기는데도 그렇다. **변별력이 가장 낮은 신호로 컷을 치는 것**이다.

```yaml
candidate-cap: 300   # 점수를 매길 후보 풀 상한. 응답 개수(limit)와 무관하다.
```

- **상한 자체는 필요하다.** 5km 안 10,000마리를 전부 채점할 수는 없다 —
  "recall 후 rank"는 추천 시스템의 표준 구조이고, 문제는 상한의 **크기**다
- **반경 확장 판정은 `limit` 기준을 유지한다.** `candidateCap` 기준으로 판정하면
  항상 상한까지 확장된다
- **페이징의 최대 깊이가 `candidateCap`이다.** 301번째 후보에는 어떤 커서로도 도달할
  수 없다 — 버그가 아니라 의도된 상한이다
- `PropertiesBindingTest`가 `candidateCap > limit 상한(100)`을 검증한다

⚠️ **콜드스타트 구간에서는 증상이 안 보인다.** 후보가 20마리도 안 되므로 `LIMIT`이
아무것도 자르지 않는다. **서비스가 성장하는 바로 그 시점에 문제가 시작된다.**

**반경 확장 단계**: `1km → 2km → 3km → 5km`
결과가 `limit` 미만이면 다음 단계로 넓혀 재조회하고, 최종 적용 반경을
`applied_radius_km`로 응답에 담는다.

⚠️ **반경은 첫 페이지에서 확정하고 cursor에 인코딩한다.** 페이지마다 반경을 다시
계산하면 페이지 사이에 후보 집합이 바뀌어 중복·누락이 생긴다.

**제외 대상**: 본인 소유 강아지 / 차단 관계(양방향) / **이미 친구인 견주의 강아지 전부** /
pending 신청이 있는 상대

⚠️ "이미 친구"는 **견주 단위**로 판정한다(2026-08-27 결정 — friendship 이 견주 쌍에
유일하다). 내 몽이가 상대의 두부와 친구가 되면 **내 초코의 추천에서도 그 견주의
강아지가 전부 빠진다.** 이미 채팅방이 있는 상대를 다시 추천하는 것은 소음이기 때문이다.

## 7. 서버 설정 (`application.yml`)

실제 구현 기준(2026-08-27). 바인딩 클래스는 `RecommendationProperties`,
`DogProperties`, `UserProperties`.

```yaml
kkodong:
  # 태그·슬롯은 '입력 검증'(dog/user)과 '점수 계산'(recommendation) 양쪽에서 쓰인다.
  # recommendation 아래 두면 강아지 등록이 추천 설정을 읽게 되어 의존 방향이 뒤집힌다.
  # → 소유 도메인 아래 두고, recommendation이 참조한다.
  dog:
    personality:
      # 키가 곧 DB에 저장·전송되는 값이다. 값은 이유 문장 조립용 두 형태(5절):
      #   stem      : 나열할 때      → "활발·사교적인 성격이…"
      #   adnominal : 명사 수식형    → "둘 다 활발한 성격이에요"
      tags:
        "[활발함]":     { stem: 활발,   adnominal: 활발한 }
        "[차분함]":     { stem: 차분,   adnominal: 차분한 }
        "[사교적]":     { stem: 사교적, adnominal: 사교적인 }
        "[낯가림]":     { stem: 낯가림, adnominal: 낯가리는 }
        "[겁많음]":     { stem: 겁많음, adnominal: 겁많은 }
        "[장난꾸러기]": { stem: 장난기, adnominal: 장난기 많은 }
        "[독립적]":     { stem: 독립적, adnominal: 독립적인 }
        "[애교많음]":   { stem: 애교,   adnominal: 애교많은 }

  user:
    walk-time-slot:
      # ⚠️ 성향 태그와 반대다 — 여기서는 **키가 API·DB 계약**이고 값은 표시용이다.
      #    그래서 자유롭게 바꿀 수 있는 것은 표시 이름뿐이고, 키가 아래 6개와
      #    다르면 서버가 기동을 거부한다(영문 키라 "moring" 같은 오타가 안 보인다).
      # 값은 이유 문장에 그대로 들어간다: "{값}에 산책하는 것도 같아요"
      slots:
        dawn: 새벽
        morning: 아침
        noon: 낮
        afternoon: 오후
        evening: 저녁
        night: 밤

  recommendation:
    max-radius-km: 5              # distance_score 정규화 기준 + 확장 상한
    radius-steps-km: [1, 2, 3, 5] # 자동 확장 단계
    neutral-score: 0.5            # 데이터 미입력 시 중립값
    age-tolerance-months: 36      # age_score가 0이 되는 나이 차
    weights:                      # 합계 100 (읽기 쉬우라고)
      distance: 30
      time-slot: 15               # ★ 2026-08-27 신설
      personality: 20
      age: 15
      size: 12
      breed: 8
      gender: 0                   # 초기 미사용 (2절 참조)
      neutered: 0                 # 초기 미사용
```

**전부 설정값이어야 하는 이유**: 이 숫자들의 유일한 검증 수단이 실사용 데이터인데,
값을 바꿀 때마다 재배포해야 하면 사실상 튜닝을 안 하게 된다.

⚠️ **개수 제한(최대 3개)은 설정에 없다.** DTO의 `@Size`와 DB CHECK 제약
(`chk_dogs_personality_traits`, `chk_users_walk_time_slots`)이 담당한다 — DB 제약을
바꾸려면 어차피 마이그레이션이 필요해 진짜로 동적일 수 없다. 동적이어야 하는 것은
'값 목록'이지 '개수'가 아니다.
