# 마킹 스팟 명세 (WALK-4)

2026-09-04 신설. `walk_bathroom_logs`(WALK-2)를 재료로 **"이 자리에 다녀간 강아지"**를
지도에 드러내는 기능의 구현 명세다.

> **이 문서는 착수 순서를 바꾸자는 제안이 아니다.** WALK-2 스키마(V6)를 짜기 **전에**
> 확정돼야 하는 항목이 있어서 지금 쓴다. 어떤 항목이 소급 가능하고 어떤 항목이
> 불가능한지는 3.2절에 명시했다 — **불가능한 것은 두 개뿐**이고, 나머지는 나중에
> 백필할 수 있다.

## 0. 한 줄 정의

**개들은 이미 서로 소통하고 있다.** 전봇대에 오줌을 싸고, 다음 개가 그 냄새를 맡는다.
시간축으로 흩어진 비동기 메시지 교환이다. 이 기능은 그것을 **만드는 게 아니라
화면에 드러내는 것**이다.

**최종 목적은 지도가 아니다.** 낯선 개를 *"이번 주에 여덟 번 마주친, 이름 아는 개"*로
바꿔서 친구 신청(FRIEND-2)의 심리적 장벽을 낮추는 것이다. 지도는 수단이다.

## 1. 왜 이 기능인가 — 콜드스타트 수학

이 제품의 진짜 문제는 밀도가 아니라 **동시성**이다. 온천천 관측 "개는 다니지만 모이지
않는다"는 개가 없다는 뜻이 아니라 **이미 같은 길을 다니는데 시간이 어긋난다**는 뜻이다
(`../product/MARKET.md` 4절 ②).

| 기능 | 화면에 보이는 양 | 유저 5명일 때 |
|---|---|---|
| 추천 피드(FRIEND-1) | `유저수` 에 비례 | 4마리. **내일도 4마리** |
| 채팅·매칭(CHAT) | `유저수²` (동시 존재 필요) | 사실상 0 |
| **마킹 스팟** | **`유저수 × 일수 × 산책당 배변횟수`** | **2주 뒤 핀 약 350개** |

추천 피드는 유저가 안 늘면 영원히 안 늘지만, 마킹 스팟은 **같은 유저가 계속 쓰기만
해도 쌓인다.** 이것이 "밀도를 올린다"가 아니라 **"필요한 밀도를 낮춘다"**는 접근이고,
1인 개발 규모에서 승산이 있는 유일한 방향이다.

**그리고 상대의 응답이 필요 없다.** 친구 신청 수락률이 낮은 건 알고리즘 탓이 아니라
신청이라는 행위 자체가 심리적으로 비싸기 때문이다. 마킹 스팟은 신청·수락·거절이
없으므로 그 비용이 0이다. MEET-2(상호 확인)와 같은 계열의 설계다.

**신규 수집 데이터는 0개다.** WALK-2가 어차피 모으는 좌표+시각을 재료로 쓴다.
API 하나 + 지도 핀 레이어면 된다.

## 2. 설계 원칙 (불변 — 어기면 "배변 지도"가 된다)

이 6개는 취향이 아니라 **기능의 성립 조건**이다.

### 2.1 핀의 주인공은 배변이 아니라 강아지다

핀을 탭했을 때 나오는 것:

```
[누끼 이미지]  두부
              푸들 · 오늘 아침쯤 다녀갔어요
```

- **똥/오줌 구분은 UI에 절대 드러내지 않는다.** 전부 "다녀감"으로 통일한다.
  데이터로는 구분해 저장한다(PET-2 건강 신호로 쓸 여지가 있다)
- 기능 이름·아이콘은 **발자국/마킹** 계열로 간다. "배변 지도"는 금지
- 누끼(`dogs.cutout_image_url`)가 여기서 핵심 자산이 된다 — ONBOARD-3이 누끼를
  온보딩에 넣은 이유가 이 화면에서 회수된다

### 2.2 25m 타일로 group by — 개별 좌표로 찍으면 기능이 성립하지 않는다

도심 GPS 오차는 10~50m다. 원좌표로 핀을 찍으면 **같은 나무에 남긴 기록이 사방에
흩어져** "여기 3마리 다녀감"이 절대 안 만들어진다. 핀 하나 = 타일 하나다.

타일 정의는 MEET-2(`walk_encounters.tile_id`)와 **반드시 동일한 함수를 쓴다** — 4절.

### 2.3 `count(DISTINCT dog_id)`

한 마리가 다섯 번 싼 것을 5마리로 세면, 첫 유저가 자기 기록만 보고 "여기 인기
많네"라고 착각하는 가짜 화면이 된다. 이 기능의 신뢰가 첫날 무너진다.

### 2.4 프라이버시는 옵션이 아니라 기능의 일부다

**이 4개가 빠지면 이 기능은 동네 사람 추적 도구다.** 전부 필수:

| 규칙 | 왜 |
|---|---|
| **최소 1시간 지연 노출** | 실시간이면 "지금 저 사람 어디 있나" 도구가 된다 |
| 시각은 "오늘 아침" 수준으로 흐림 | 분 단위 노출 금지. 반복되면 생활 패턴이 특정된다 |
| 각 유저 `home_location` **반경 200m 내 기록은 타인에게 비노출** | 집 앞 마킹은 곧 주소다. `home_location` 흐림 처리가 무의미해진다 |
| 차단 관계 **양방향** 제외 | SAFETY-1이 적재만 하고 있는 차단을 **여기서 실제로 적용**해야 한다 |

+ **끄기 옵션 필수**(2.5·3.2 참조).

### 2.5 궤적이 아니라 배변 지점만 쓴다

궤적(`walk_sessions.route`)은 "이 사람이 어디를 어떻게 다녔는지"라 **이동 이력 그
자체**지만, 배변 지점은 전봇대·나무 같은 **공공 지형지물에 대한 정보**고 정보량이
훨씬 적다. 이 구분이 2.4의 정당성을 지탱한다.

⚠️ **궤적을 이 기능에 끌어들이자는 제안이 나오면 거절할 것.** 편해 보이지만 이
기능의 프라이버시 논거 전체가 무너진다. (`walk_encounters`가 좌표·시각을 저장하되
**API 응답에 절대 포함하지 않는** 것과 같은 원칙이다.)

### 2.6 주 무대는 지도 탭이 아니라 산책 중 화면

걷다가 화면을 보면 앞쪽에 핀이 보이고, 실제로 그 나무에 다다랐을 때 *"아, 여기
두부가 다녀갔구나"*가 되는 것. 이게 이 기능의 전부다. 별도 탭에 넣으면 "가끔 열어보는
지도"가 되고 아무 일도 일어나지 않는다.

- 내 개 기록과 남의 개 기록은 **시각적으로 확실히 구분**한다
- 산책이 끝난 뒤에도 보이지만(지난 산책 다시보기), 주 동선은 산책 중이다

## 3. 데이터 모델

### 3.1 `walk_bathroom_logs` 변경점 (V6에 반영)

`DB_SCHEMA.sql`의 현재 계획본에서 **두 컬럼을 추가**한다.

```sql
CREATE TABLE walk_bathroom_logs (
    id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    walk_session_id UUID NOT NULL REFERENCES walk_sessions (id) ON DELETE CASCADE,
    client_log_id TEXT,
    type TEXT NOT NULL CHECK (type IN ('poop', 'pee')),
    location GEOGRAPHY(POINT, 4326),
    logged_at TIMESTAMPTZ NOT NULL DEFAULT now(),

    -- ▼ WALK-4 신설 ▼

    -- 비정규화. 원본은 walk_sessions.dog_id 지만, 타일 집계는
    --   count(DISTINCT dog_id) GROUP BY tile_id 한 방으로 끝나야 하고
    --   매 조회마다 walk_sessions 를 조인하면 지도 팬/줌마다 비용이 붙는다.
    --   (walk_sessions.poop_count 를 비정규화한 것과 같은 판단)
    dog_id UUID NOT NULL REFERENCES dogs (id) ON DELETE CASCADE,

    -- location 에서 파생. 저장하는 이유는 성능이다 —
    --   지도 조회의 WHERE 는 항상 타일 집합이지 좌표가 아니다.
    --   location 이 NULL 이면 tile_id 도 NULL 이고, 이 기록은 지도에 안 나온다.
    tile_id BIGINT
);

-- [조회 성능] 지도 조회의 유일한 동선: "이 타일들에서 최근 N일" 
CREATE INDEX idx_walk_bathroom_logs_tile
    ON walk_bathroom_logs (tile_id, logged_at DESC)
    WHERE tile_id IS NOT NULL;
```

**`users`에 공개 설정 컬럼을 추가한다.**

```sql
-- 기본값 논의는 3.3절. 값이 무엇으로 정해지든 컬럼은 V6에 있어야 한다.
ALTER TABLE users
    ADD COLUMN marking_sharing_enabled BOOLEAN NOT NULL DEFAULT true;
```

### 3.2 ⚠️ 무엇이 소급 가능하고 무엇이 불가능한가

`../TICKETS.md`는 WALK 스키마에 대해 "타일 + 타임스탬프 소급 불가"라고 적어뒀지만,
**배변 기록에 한해서는 정확히 두 가지만 불가능하다.** 나머지는 백필된다.

| 항목 | 소급 | 근거 |
|---|---|---|
| `dog_id` | ✅ 가능 | `walk_session_id` → `walk_sessions.dog_id` 조인으로 백필 |
| `tile_id` | ✅ 가능 | `location`에서 계산해 백필. 저장은 순전히 성능 목적 |
| 시각 흐림·1시간 지연 | ✅ 가능 | 표시 단계 로직. 원본은 정확히 저장한다 |
| `home_location` 200m 마스킹 | ✅ 가능 | 조회 시점 계산 |
| **`location`이 실제로 채워지는가** | 🔴 **불가능** | 컬럼은 nullable이고 "GPS 순간 불가 대비"가 명분이다. 하지만 **클라이언트가 좌표를 안 담고 보내면 그 기록은 영원히 핀이 될 수 없다.** WALK-2 클라이언트 구현에서 좌표 확보를 최선으로 시도해야 한다 |
| **공개 동의 상태** | 🔴 **불가능** | 3개월치 기록을 쌓아놓고 나서 "이걸 공개해도 됐던 건가"를 되물을 수 없다. 기본값을 **지금** 정하고, 기록 시점의 상태를 존중해야 한다 |

> 즉 이 문서가 WALK-2 착수 전에 필요한 진짜 이유는 **컬럼 두 개가 아니라 위 빨간 줄
> 두 개**다. 컬럼은 늦게 넣어도 백필된다.

### 3.3 공개 기본값 — 결정 필요 🟠

| 안 | 장점 | 단점 |
|---|---|---|
| **A. 기본 공개(opt-out)** | 밀도가 확보된다. 유저 5명일 때 opt-in이면 화면이 그냥 빈다 | 동의 없이 공개했다는 인상 |
| B. 기본 비공개(opt-in) | 안전 | **기능이 사실상 죽는다.** 초기 유저가 설정을 찾아 켤 이유가 없다 |

**권고: A(기본 공개) + 온보딩에서 명시적 고지 + 마이 탭 1탭 끄기.**
근거는 노출 정보가 2.4의 4중 마스킹을 거친 뒤라는 것이다 — 1시간 지연 + 흐린 시각 +
집 주변 제외 + 강아지 이름/누끼만. 다만 **온보딩에서 이 기능을 설명하지 않고 A를
택하면 안 된다.** ONBOARD-1(안전 고지) 화면에 한 줄이 들어가야 한다.

## 4. 타일 정의 — MEET-2와 공유 🟠 결정 필요

`../product/MARKET.md` 4절 ⑥은 "20~25m 격자, **H3 res11 또는 지오해시 8자리**"로
열어뒀다. 마킹 스팟과 MEET-2가 **같은 함수를 써야** 하므로 여기서 하나로 못박는다.

**권고: H3 res11** (`com.uber:h3`, 평균 변 길이 약 24.9m)

| | H3 res11 | 지오해시 8자리 | 직접 만든 격자 |
|---|---|---|---|
| BIGINT 적합 | ✅ 64비트 인덱스 그대로 | ❌ 문자열(11자) | ✅ |
| 셀 모양 | 육각형, 위도 무관하게 균일 | **38m × 19m 직사각형** | 위도별 경도 보정 필요 |
| 인접 타일 | `gridDisk(h, 1)` 한 줄 | 8방향 수동 계산 | 수동 |
| 의존성 | 라이브러리 추가 | 없음 | 없음 |

**인접 타일 조회가 결정적이다.** MEET-2의 스침 판정이 "동일 타일 **또는 인접 타일**"
(`../TICKETS.md` MEET-2)이고, 마킹 스팟도 지도 뷰포트를 타일 집합으로 바꿔야 한다.
H3는 이게 한 줄이고 나머지는 전부 손으로 짜야 한다. `tile_id BIGINT`가 이미
`walk_encounters`에 잡혀 있는 것도 H3 인덱스를 전제한 형태다.

**타일 계산은 서버에서 한다.** 클라이언트가 계산해 보내면 iOS/Android/버전별로
격자가 달라지는 순간 복구가 불가능하다.

```java
// 공용 유틸. MEET-2 · WALK-4 가 함께 쓴다.
// global/util/Tiles.java
public final class Tiles {
    public static final int RESOLUTION = 11;   // 설정값으로 뺄 것
    public static long of(double lat, double lng) { ... }
    public static List<Long> disk(long tileId, int k) { ... }
}
```

⚠️ **해상도는 절대 나중에 바꿀 수 없다.** 바꾸면 기존 `tile_id`가 전부 무의미해지고,
`location`이 NULL인 행은 재계산조차 못 한다. 설정값으로 빼되 **운영 중 변경 금지**로
주석을 달 것.

## 5. API

`API_SPEC.md` 5절(산책 기록) 아래 **5.4**로 들어간다.

### 5.4 마킹 스팟 (WALK-4)

| 동작 | 메서드/경로 | 상세 |
|---|---|---|
| 마킹 스팟 조회 | `GET /api/v1/marking-spots` | query: `lat`, `lng`, `radiusMeters`(기본 500, 최대 2000), `days`(기본 7, 최대 30) |
| 공개 설정 변경 | `PATCH /api/v1/users/me` | body에 `markingSharingEnabled` 추가(기존 프로필 수정 재사용 — 새 엔드포인트 안 만든다) |

**응답**

```jsonc
{
  "spots": [
    {
      "tileId": 622054503267303423,
      "lat": 35.1798,          // 타일 중심점. 원좌표가 아니다
      "lng": 129.0756,
      "dogCount": 3,           // count(DISTINCT dog_id)
      "isMine": false,         // 내 강아지 기록이 포함돼 있는가
      "dogs": [                // 최대 5마리. dogCount 가 더 클 수 있다
        {
          "dogId": "…",
          "name": "두부",
          "breed": "푸들",
          "cutoutImageUrl": "…",
          "visitedAtLabel": "오늘 아침쯤"   // ★ 서버가 문자열로 내려준다
        }
      ]
    }
  ]
}
```

**설계 메모**

- ⚠️ **`lat`/`lng`는 타일 중심점이지 원좌표가 아니다.** 원좌표를 내려주면 25m 타일로
  뭉갠 의미가 사라진다
- ⚠️ **`visitedAtLabel`은 서버가 완성된 문자열로 내려준다.** 타임스탬프를 내려주고
  클라이언트가 포맷하게 하면, **API 응답에 정확한 시각이 남는다** — 프록시로 뜯어보면
  그대로 이동 이력이다. 2.4의 "흐림"은 표시 규칙이 아니라 **응답 계약**이다
- `type`(poop/pee)은 **응답에 없다**(2.1)
- `dogs` 배열은 최대 5마리까지만. 그 이상은 `dogCount`로만 표현한다

**에러 코드** (`ErrorCode`에 추가)

| 코드 | 상황 |
|---|---|
| `W001` | 조회 반경이 상한(2000m) 초과 |

## 6. 조회 로직

```sql
SELECT b.tile_id,
       count(DISTINCT b.dog_id) AS dog_count
  FROM walk_bathroom_logs b
  JOIN dogs  d ON d.id = b.dog_id
  JOIN users u ON u.id = d.owner_id
 WHERE b.tile_id = ANY(:tileIds)              -- 뷰포트 → H3 gridDisk
   AND b.logged_at >= now() - (:days || ' days')::interval
   AND b.logged_at <= now() - interval '1 hour'          -- 2.4 지연 노출
   AND u.marking_sharing_enabled                          -- 3.3 공개 설정
   AND u.id <> :me                                        -- 내 기록은 별도 조회
   AND u.id <> ALL(:blockedUserIds)                       -- 2.4 차단 양방향
   AND NOT ST_DWithin(u.home_location, b.location, 200)   -- 2.4 집 주변 제외
 GROUP BY b.tile_id;
```

**주의**

1. `blockedUserIds`는 `BlockRepository.findRelatedUserIds`를 재사용한다 —
   **차단한/차단당한 양방향**이어야 한다(FRIEND-1의 후보 제외와 같은 목록)
2. `ST_DWithin`의 기준은 **기록 주인의 집**이지 조회자의 집이 아니다.
   반대로 걸면 "내 집 주변에 아무것도 안 보이는" 이상한 화면이 된다
3. 내 강아지 기록은 위 쿼리에서 제외하고 **별도로 조회해 합친다** — 지연 노출·
   집 주변 제외 규칙이 내 기록에는 적용되지 않아야 한다(2.6의 시각적 구분)
4. `dogs` 배열은 타일별 상위 5개를 `DISTINCT ON (dog_id) ... ORDER BY logged_at DESC`로
   따로 뽑는다. 위 집계와 한 쿼리에 욱여넣지 말 것

## 8. 클라이언트 규칙 (WALK-2와 함께 구현)

### 8.1 기록 버튼은 한 번 탭으로 끝나야 한다

**이 기능 전체가 이 한 줄에 달려 있다.** 참여율이 죽으면 핀이 안 쌓이고, 핀이 안
쌓이면 기능이 없는 것과 같다.

- 똥/오줌 **종류 선택조차 두 번째 탭으로 미룬다**. 첫 탭에 즉시 기록되고,
  종류는 그 뒤에 바꿀 수 있게
- 좌표는 탭 순간의 마지막 위치를 즉시 쓴다. GPS 정밀도를 기다리지 않는다
  (25m 타일로 뭉개므로 정밀도보다 **누락**이 훨씬 나쁘다 — 3.2)
- 오프라인 큐 + `clientLogId` 멱등키는 `API_SPEC.md` 5.2에 이미 있다

### 8.2 표시

- 산책 중 지도 위 레이어. 내 개 기록과 남의 개 기록 시각 구분
- 핀 탭 → 누끼 + 이름 + 견종 + `visitedAtLabel`
- **핀에서 곧바로 친구 신청(FRIEND-2)으로 갈 수 있어야 한다.** 이게 이 기능의 회수
  지점이다 — 지도만 보고 끝나면 만든 의미가 없다

## 9. FRIEND-1과의 연결 — 별개 기능이 아니다

`RECOMMENDATION.md` 2절이 예고한 **"시간대 신호 2단계 — 온보딩 선언값을
실측으로 보정"**의 그 실측 데이터가 정확히 이 로그다.

```
walk_bathroom_logs.logged_at  →  강아지별 실제 산책 시간대 분포
                              →  users.walk_time_slots(선언값) 보정
                              →  time_slot_score 정확도 상승
```

⚠️ 단, **선언값 컬럼을 덮어쓰지 않는다.** 유저가 입력한 값과 실측값은 다른 데이터다.
보정은 점수 계산 단계에서 두 값을 섞는 방식이어야 하며, 실측 반영 시점·비율은
Phase 1 데이터를 보고 정한다.

## 10. 알려진 약점 (정직하게)

| # | 약점 | 대응 |
|---|---|---|
| 1 | **기록 버튼 참여율에 전적으로 의존.** 이게 죽으면 기능 전체가 죽는다 | 8.1. 이 기능의 유일한 단일 실패점이다 |
| 2 | 유저 5명이면 매번 **같은 3마리**가 뜬다 | 누적이 시간을 벌어줄 뿐 만능이 아니다. MEET-1(운영자 모임)과 병행해야 한다 |
| 3 | **불쾌하게 느끼는 사람이 반드시 있다** | 옵트아웃 필수(3.3). 이걸 "설정 깊은 곳"에 숨기지 말 것 |
| 4 | 겨울·우천에 산책 자체가 줄면 핀도 준다 | `days` 기본값 7일을 계절에 따라 늘리는 것으로 흡수 가능(설정값) |

### 검증 가설 (Phase 1 데이터로 확인)

1. **기록 버튼 탭률** — 산책 1회당 배변 기록 수. 실제 배변 횟수(1~3회)에 근접하는가,
   아니면 1회 미만인가. 1회 미만이면 8.1을 다시 설계해야 한다
2. **핀 → 친구 신청 전환율** — 마킹 스팟을 본 유저의 신청률이 추천 피드만 본 유저보다
   높은가. **이 기능의 존재 이유를 검증하는 유일한 지표다**
3. **옵트아웃 비율** — 10%를 넘으면 2.4의 마스킹이 부족하다는 신호다

## 부록. 이 기능이 아닌 것

콜드스타트 논의에서 함께 나왔지만 **이 문서의 범위가 아닌** 것들. 혼동 방지용으로만
적어둔다.

| | 무엇 | 상태 |
|---|---|---|
| 꼬동 태그 | 목줄 QR 스티커. 오프라인 획득 + 개 목줄이 광고면 | 물리 굿즈라 1인 개발 범위 초과 위험. 초기 100명 한정으로만 검토 |
| 루틴 공개 | `walk_time_slots`를 표면으로 꺼내 "오늘 저녁 이 구간에 4마리" | 별도 검토. 생성·초대·참석확인이 없으므로 `../product/MARKET.md` 6절의 "모임 기능 금지"에 걸리지 않는다 |
| 방향·구간 매칭 | 온천천이 선형이라 반대 방향이면 반드시 마주친다 | ⚠️ **WALK-1이 궤적에 진행 방향을 파생 가능하게 저장해야 하고 소급 불가.** 별도 결정 필요 |

**하지 말 것**: 가짜 프로필 시딩(동네 기반이라 들키면 복구 불가), 커뮤니티로 콜드스타트
해결(`../product/MARKET.md` 6절이 이미 금지), 추천 알고리즘 정교화로 해결 시도
(후보가 3마리면 가중치를 어떻게 바꿔도 3마리다).
