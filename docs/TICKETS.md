# TICKETS.md — 꼬동 Phase 1

`product/CONCEPT.md`(v3, 2026-08-15) 기준 Phase 1 티켓 분해.
v2 기준으로 작성됐던 이전 버전은 이 문서로 대체됨(모집글 기반 매칭 티켓 MAP-1~3 삭제,
FRIEND/WALK/COMMUNITY 계열 신설).

**Phase 1 목표**: **강아지 친구가 실제로 생기는가**를 검증한다. 추천 → 신청 → 수락 →
채팅 → 산책 약속 → 만남 → 카드 공유까지 한 바퀴가 돌아가는 것이 Phase 1의 완성 조건.
매장·예약·점주앱(Phase 3), 커머스(Phase 4)는 **착수 금지** — 범위 폭증이 이 프로젝트의
가장 큰 리스크다(product/CONCEPT.md 7절).

**공통 원칙**:
- 백엔드: **Java Spring Boot 자체 서버**(`kkodong-server/` — 2026-08-19에 `server/`에서 리네임), DB는 Supabase Postgres 호스팅만
- 패스권(Free/Plus/Pro) 분기 로직은 View가 아닌 ViewModel/서비스 레이어에 배치
- 각 티켓은 브랜치 1개 (`feature/티켓번호-요약`)
- API 경로/계약은 `design/API_SPEC.md`, `design/openapi.yaml` 참조
- 스키마 변경은 **새 Flyway 마이그레이션 파일**로. V1~V5가 적용돼 있으므로 **다음은
  V6**다. 적용된 파일은 체크섬 검증 때문에 주석 한 글자도 못 고친다
  (design/DB_SCHEMA.sql 상단 / archive/DEV_STACK_PIPELINE.md 3.1 참조)

### 권장 착수 순서

핵심 루프를 가장 빠르게 한 바퀴 돌리는 순서. SAFETY가 FRIEND/CHAT의 선행 의존성이라는
점을 반영했다.

```
✅ 1. FOUNDATION-1 마무리 (온보딩 완료 처리, /members → /users 리네임)
✅ 2. PET-1 확장     (personality_traits / cutout_image_url / weight_kg)
✅ 3. SAFETY-1/2     (차단·신고)
🟡 4. FRIEND-1/2/3   (추천 → 신청 → 수락)                    ★ 핵심
                     └ ✅ 산책 시간대 컬럼·설정값은 V5에서 선반영 완료
                     └ ✅ 추천 후보 조회 + 차단(SAFETY-1) 양방향 제외 완료
                     └ ⬜ 점수 계산 · 이유 문장 · 커서 · FRIEND-2/3
   5. CHAT-1/2       (채팅 → 산책 약속)
   6. WALK-1/2/3     (산책 기록 → 배변 기록 → 경로 저장)
                     └ ⚠️ 타일 + 타임스탬프 기록 필수 (소급 불가)
   7. CARD-1/2       (완료 카드 → SNS 공유)
   8. MEET-2         (산책 후 "만난 강아지" 상호 확인)
   9. COMMUNITY-1/2
  10. PET-2, PASS-1
  11. FOUNDATION-2 / ONBOARD-1 / ONBOARD-3 (클라이언트 진행과 병행)

  ※ MEET-1(운영자 산책 모임)은 코드가 없으므로 이 순서 바깥에서
     베타 오픈 시점에 병렬로 진행한다.
```

## FOUNDATION — 인증 & 앱 진입 구조

**다른 모든 티켓의 전제조건이다.**

### FOUNDATION-1. 회원가입/로그인
- **내용**: Spring Security + 자체 JWT(AT/RT) 기반 이메일 회원가입/로그인 +
  Sign in with Apple, 세션 유지/로그아웃. 클라이언트는 `/api/v1/auth/*` REST 호출 +
  받은 토큰을 Keychain에 저장/자동 첨부/만료 시 갱신.
- ✅ **완료(2026-08-27)**: 온보딩 완료 처리(`PATCH /users/me/onboarding`),
  `/api/v1/members/*` → `/api/v1/users/*` 리네임(DB 테이블명 `users` 및 전체 문서와 일치).
- **남은 작업** (상세: `design/API_SPEC.md` "미해결" 절):
  1. 🔴 온보딩 선행조건에서 **산책 시간대 필수 조건을 제거**. 지금은 시간대를
     건너뛴 유저가 온보딩을 완료할 수 없어 앱에 진입하지 못한다 —
     "건너뛰기 허용"(ONBOARD-3)과 정면으로 충돌한다
  2. 프로필 응답(`UserResponse`)에 `walkTimeSlots` 추가 — 저장은 되는데 되받을 수
     없어 온보딩 UI가 선택 상태를 복원하지 못한다
  3. 탈퇴 시 Redis Refresh Token 즉시 폐기(현재는 자연 TTL 7일까지 살아 있다)
- **카카오/구글 로그인**: 제품 흐름은 결정됨(v2 8절)이나 기술 명세 미정(TICKETS.md Q7).
  **Apple 심사 가이드라인 4.8** — 제3자 소셜 로그인을 넣으면 Sign in with Apple도
  동등하게 제공해야 하는데 이미 있으므로 요건은 충족. Phase 1 후반 추가 가능.
- **수익 모델 영향**: 없음(인프라).

### FOUNDATION-2. 메인 화면 & 탭 내비게이션
- **내용**: 앱 루트 라우팅 — 스플래시 → 로그인 여부 → (비로그인) 로그인 화면 →
  (로그인, 온보딩 미완료) 온보딩 → (완료) 메인 TabView.
- **v3 탭 구성** (v2의 지도/피드/채팅/케어에서 변경):

  | 탭 | 내용 | 관련 티켓 |
  |---|---|---|
  | **친구** | 주변 강아지 추천 피드, 받은 신청, 친구 목록 | FRIEND-1/2/3 |
  | **산책** | 산책 시작/기록, 지난 경로 | WALK-1/2/3, CARD-1/2 |
  | **커뮤니티** | 자유 게시판 | COMMUNITY-1/2 |
  | **채팅** | 친구별 1:1 채팅, 산책 약속 | CHAT-1/2 |
  | **마이** | 반려견 프로필, 케어 알림, 패스권, 설정 | PET-1/2, PASS-1, SAFETY |

  ⚠️ **"친구" 탭이 첫 번째 탭이자 앱 기본 진입 화면이다** — 핵심 기능이 무엇인지
  정보구조가 그대로 말하게 한다.
- **수익 모델 영향**: 없음(인프라).

### ONBOARD-2. 서비스 지역 게이팅 🟠 보류

### ONBOARD-3. 강아지 등록 + 누끼 생성 ★v3 신설
- **내용**: 온보딩에서 강아지 사진 촬영 → **Vision `VNGenerateForegroundInstanceMaskRequest`
  (iOS 17+, 온디바이스)로 배경 제거** → 누끼 이미지 미리보기/확정 → 업로드
  (`POST /dogs/{dogId}/cutout`) → `dogs.cutout_image_url` 저장.
  같은 화면에서 이름·견종·생일·체급·**성향 태그**·**주로 산책하는 시간대**도 함께
  입력받는다.
- **왜 온보딩에 넣는가**: 누끼 이미지가 프로필·추천 피드·산책 카드 전체를 관통하는
  브랜드 자산이라(product/CONCEPT.md 3.5), 나중에 유도하면 대부분 안 만든다.
- **수익 모델 영향**: 간접 — 카드 품질이 곧 SNS 공유율이고, 카드 커스터마이징이
  패스권 전환 포인트다.
- **주의**: 배경 제거 실패(어두운 사진, 여러 마리 등)에 대비해 **원본 사진 사용
  폴백**을 반드시 넣는다. 누끼 없이는 진행 불가로 만들면 온보딩 이탈이 생긴다.
- **성향 태그 UI** (2026-08-15 확정 — TICKETS.md Q10):
  **8개 중 최대 3개 선택, 건너뛰기 허용**

  ```
  활발함  차분함  사교적  낯가림  겁많음  장난꾸러기  독립적  애교많음
  ```

  - 3개를 채우도록 강요하지 않는다(0개도 유효) — 태그 미입력은 추천에서 중립(0.5)으로
    처리되므로 불이익이 없다
  - "나중에 프로필에서 바꿀 수 있어요"를 명시 — 첫 입력의 부담을 낮춘다
- **산책 시간대 UI** (2026-08-27 신설 — `design/RECOMMENDATION.md` 2절):
  **6개 중 최대 3개 선택, 건너뛰기 허용**

  ```
  새벽(05~08)  아침(08~11)  낮(11~15)  오후(15~18)  저녁(18~21)  밤(21~24)
  ```

  - 최대 3개 제한은 **DB CHECK 제약**으로 건다(`chk_users_walk_time_slots`, V5 적용
    완료). 상한이 없으면 전부 고른 유저가 모두와 100% 겹쳐 추천 상위를 독식한다
  - 미입력은 중립(0.5) 처리라 불이익이 없다
  - ⚠️ **현재 서버는 시간대가 비면 온보딩 완료를 거부한다**(400 `M006`) —
    "건너뛰기 허용"과 충돌하므로 FOUNDATION-1 잔여 작업에서 고친다

## FRIEND — 강아지 친구 ★★핵심

### FRIEND-1. 주변 강아지 추천 피드

**진행 상황 (2026-09-07)**

| | |
|---|---|
| ✅ | 선행 검증 — `home_location` 미설정(F001) · 타인 강아지 조회(F002) |
| ✅ | 제외 집합 — 차단 양방향(SAFETY-1) + 이미 친구인 견주(견주 단위 판정) |
| ✅ | PostGIS 후보 조회 (`ST_DWithin` + GiST) · 응답 조립 · 커밋 `c80826b` |
| ⬜ | `RecommendationScorer` — 6개 신호 점수·합산·동점 셔플. **핵심이자 미착수** |
| ⬜ | `RecommendationReasonBuilder` — 이유 문장 |
| ⬜ | `RecommendationCursor` — 반경/오프셋 인코딩. 지금은 반경이 상한 5km 고정이고 `1→2→3→5km` 자동 확장이 없다 |
| ⬜ | 견종 그룹 테이블 — `breed_score`의 입력인데 설정에 아직 없다 |
| ⬜ | `DogResponse.publicInfo`에 `id`·`ageMonths` 추가 — 없으면 클라이언트가 신청 대상 id를 못 받는다 |

⚠️ **후보 풀 상한(`candidate-cap`)은 요청 `limit`과 별개 설정값이다.** 같은 값으로
두면 가까운 순 `limit`개만 뽑아 재정렬하는 꼴이라 거리가 하드 필터로 작동해 아래
"필수 설계 제약" 1번이 무력해진다. 근거와 수치는
[`design/RECOMMENDATION.md`](design/RECOMMENDATION.md) 6절.

- **내용**: `users.home_location` 기준 반경 내 강아지를 **가중치 랭킹**으로 정렬해
  카드 형태로 노출. 신호: 거리 / **산책 시간대** / 성격 태그 / 나이 / 견종 / 체급
  (+보조: 성별·중성화).
- **📄 구현 명세: [`design/RECOMMENDATION.md`](design/RECOMMENDATION.md)**
  (2026-08-15 확정, TICKETS.md Q10 해결). 점수 공식·신호별 계산식·견종 그룹 테이블·
  이유 문장 템플릿·`application.yml` 설정 구조가 전부 여기 있다. **착수 전 필독.**
- **점수 공식** (2026-08-27 개정 — 시간대 신설):
  `30×거리 + 15×산책시간대 + 20×성격 + 15×나이 + 12×체급 + 8×견종` (성별·중성화는 0)
  - ✅ **`users.walk_time_slots` 컬럼은 `V5__add_friend_domain.sql`에 동봉 완료.**
    설정값(`kkodong.recommendation.weights.time-slot: 15`)과 입력 API
    (`PATCH /users/me`)까지 준비돼 있다 — 남은 것은 점수 계산 코드뿐이다
  - 온보딩 **선언값**으로 받으므로 밀도 0에서도 작동한다(성향 태그와 동일한 방식)
- **필수 설계 제약** (이걸 어기면 v2에서 HOLD됐던 콜드스타트 문제가 그대로 재발한다):
  1. **성격·견종·나이를 WHERE 조건(하드 필터)으로 쓰지 않는다.** 전부 ORDER BY 가중치.
  2. 후보가 `limit` 미만이면 **반경을 `1→2→3→5km`로 자동 확장**해 재조회.
     반경은 첫 페이지에서 확정해 cursor에 인코딩(페이지마다 재계산하면 중복·누락 발생).
  3. 가중치·반경·태그 세트는 **`application.yml` 설정값으로 분리** — 재배포 없이 조정
     가능해야 한다. 검증 수단이 실사용 데이터뿐이라, 바꾸기 어려우면 튜닝을 안 하게 된다.
  4. **매칭 점수를 숫자로 노출하지 않는다.** 대신 "둘 다 활발한 성격이에요, 나이도
     비슷해요" 같은 **추천 이유 문장**을 서버가 생성해 함께 내려준다.
  5. **데이터 미입력은 0점이 아니라 중립(0.5)** — 태그·생일·체급을 건너뛴 신규 유저가
     추천 하위에 영구히 깔리면 스스로 콜드스타트를 만드는 셈이다.
  6. 점수 반올림 후 **동점 그룹 내 무작위 셔플**(시드 = user_id + 날짜) — 상위 강아지가
     응답 안 해도 계속 상위에 남아 화면이 정체되는 걸 막는다.
- **응답 위치 처리**: 상대방 좌표를 그대로 내려주지 않는다 — **거리를 정수 km로
  반올림**해서 전달(V2 마이그레이션의 흐림 원칙 유지).
- **함께 심을 것**: 신청 수·수락 수·수락 소요시간 로깅(FRIEND-2 지표). **누적 신청
  100건 전에는 가중치를 조정하지 않는다** — 소음에 반응한 튜닝은 알고리즘을 더 나쁘게 만든다.
- **수익 모델 영향**: 없음(핵심 무료 루프). 다만 모든 수익 축의 전제.
- **의존성**: PET-1 확장(성향 태그), SAFETY-1(차단 유저 추천 제외).
  ~~TICKETS.md Q10~~ 해결됨. Q8(반경 상한)은 미결정이나 잠정 5km로 착수 가능.

### FRIEND-2. 친구 신청 / 수락
- **내용**: 추천 카드에서 친구 신청(한마디 메시지 선택) → 상대 견주에게 푸시 →
  받은 신청 목록에서 수락/거절. **수락 시 `@Transactional`로 `friend_requests.status`
  갱신 + `friendships` upsert + 채팅방 개설**.
- ★ **friendship 은 견주 쌍에 유일하다** (2026-08-27 결정). 신청은 강아지 단위지만
  관계는 견주 단위 — 이미 그 견주와 친구면 **새 friendship 을 만들지 않고 재사용**한다.
  강아지 쌍을 유일 단위로 두면 다견 견주에게 같은 사람과의 채팅방이 2개 생기고,
  산책 약속이 어느 friendship 에 붙어야 할지 정할 근거가 없어진다.
  저장 시 `user_a_id < user_b_id` 정렬 필수.
- **추적 지표**: **친구 신청 수락률이 이 제품의 1순위 지표다.** 신청 수·수락 수·
  수락까지 걸린 시간을 Phase 1부터 기록한다(추천 알고리즘 가중치 조정의 유일한 근거).
- **수익 모델 영향**: 없음(핵심 무료 루프).
- **주의**: 같은 쌍에 pending 신청 중복 방지(부분 유니크 인덱스), 거절/취소 후
  재신청은 허용. 차단 관계면 서버가 403.

### FRIEND-3. 친구 목록 / 강아지 프로필 상세
- **내용**: 맺어진 친구 목록, 상대 강아지 프로필 상세(누끼 사진, 성향, 견종, 나이,
  함께한 산책 횟수). 프로필에서 채팅·산책 약속·차단·신고 진입.
- **수익 모델 영향**: 없음.

- **주의**: MAP-3(구 티켓)의 **안전 넛지 문구를 여기로 옮긴다** — 첫 만남 약속이

- **주의**: 오프라인/네트워크 끊김 상황에서도 눌린 기록이 유실되지 않게 **로컬
  큐잉 후 일괄 전송**. 산책 중 네트워크는 불안정한 게 정상이다.

### WALK-3. 지난 경로 다시보기 / 저장 ★v3 신설
- **내용**: 지난 산책 기록을 지도에 다시 그려 보여주기. 마음에 든 경로는 이름을 붙여
  `saved_routes`에 저장하고, 다음 산책 시 불러오기.

## MEET — 만남 진입로 ★v3.1 신설

친구 신청 퍼널(추천 → 신청 → 수락 → 채팅 → 약속 → 만남)은 **신청 단계에서 대부분
이탈**한다. 소개팅 앱과 동일한 심리적 장벽이다. MEET 계열은 그 장벽을 우회하는
**얕은 진입로**다. 설계 근거는 [`product/MARKET.md`](product/MARKET.md) 4절 ②.

> **핵심 전환**: 마주침을 *만들려* 하지 말고(핫플레이스), **이미 일어난 마주침을
> 붙잡는다**(MEET-2). 온천천처럼 개가 흐르기만 하고 뭉치지 않는 선형 구간에서는
> 후자가 오히려 유리하다.

### MEET-1. 운영자 주최 정기 산책 모임 🟢 코드 0줄

- **내용**: 운영자가 초기 서비스 지역에서 **오프라인 정기 산책 모임**을 연다.
  "이번 주 토요일 오전 10시, 온천천 어울마당." 앱에는 **공지 한 줄** 외에 아무것도
  만들지 않는다.
- **왜 지금 하는가**: 유저 10명 구간에서는 **어떤 알고리즘도 작동하지 않는다**.
  우연을 만들 재료가 없기 때문이다. 이 구간에서 실제로 사람을 만나게 하는 유일한
  수단이 운영이다.
- **★ 진짜 목적은 가설 검증**: *"견주들이 서로 만나고 싶어하는가."*
  아무도 안 나온다면 그건 이 기능을 접을 이유가 아니라 **제품 방향 전체를 다시 볼
  신호**다. 6개월치 개발 전에 아는 편이 압도적으로 싸다.
- **장소 후보**: [`seed/oncheoncheon_hotspots.csv`](seed/oncheoncheon_hotspots.csv)
  3개 지점을 "핫플레이스"가 아니라 **모임 장소 후보**로 재활용한다.
- **수익 모델 영향**: 없음.
- **⚠️ 착수 금지 사항**: **"모임 기능"을 앱에 만들지 않는다.** 포동 등 기존 앱의
  커뮤니티에 이미 있는 기능이고, `product/MARKET.md` 6절 "커뮤니티에 힘 주기" 금지
  항목에 정면으로 걸린다. 기능화하는 순간 이 티켓의 최대 장점(코드 0줄)이 사라진다.
- **측정**: 공지 노출 수 / 실제 참석자 수 / 참석자 중 친구 연결로 이어진 쌍의 수.
  수기 기록으로 충분하다.

### MEET-2. 산책 후 "오늘 만난 강아지" 상호 확인 ★

- **내용**: 산책 종료 시 완료 카드(CARD-1)와 함께 **시간·구간이 겹쳤던 강아지**를
  후보로 보여주고 "오늘 만난 강아지가 있나요?"를 묻는다. **양쪽이 서로를 고르면
  친구로 연결**된다.
- **★ 거절이 존재하지 않는다**: 한쪽만 고르면 아무 일도 일어나지 않고 **상대는 그
  사실을 알지 못한다.** 신청도 수락도 거절 신호도 없어 퍼널 이탈 지점이 구조적으로
  제거된다. 이미 눈 마주치고 개끼리 인사시킨 사이라 심리적 비용도 낮다.
- **후보 판정** — GPS 오차(도심 10~50m)를 감안해 **시간은 좁게, 거리는 넓게**:

  ```
  동일 타일(25m) 또는 인접 타일에
  시간 창 ±5분 이내로 양쪽 궤적이 존재  →  '스침' 후보
  ```

  ⚠️ 느슨하면 "본 적 없는 개"가 뜨고, 빡빡하면 아무도 안 뜬다. 임계치는
  **`application.yml` 설정값으로 분리**한다(추천 가중치와 동일한 이유).
- **⚠️ 프라이버시 (필수)**: 후보 목록에 **스친 시각·좌표를 절대 함께 노출하지
  않는다.** 강아지 이름과 사진만 보여준다. "몇 시에 어디서 스쳤다"는 이동 이력이고,
  노출되는 순간 `home_location` 흐림이 무의미해진다.
  - 이 기능이 안전한 근거는 k-익명성이 아니라(1:1 대응이라 적용 불가)
    **"상대가 이미 나를 직접 본 사람"이라 새로 드러나는 정보가 0**이라는 데 있다.
    시각·좌표 비노출이 그 전제를 지키는 유일한 조건이다.
  - 차단(SAFETY-1) 관계는 후보에서 **양방향 제외**한다.
- **의존성**: WALK-1(경로 기록 + **타일·타임스탬프**), CARD-1, SAFETY-1.
  ⚠️ WALK 스키마에 타일·타임스탬프가 없으면 **소급이 불가능**하다.
- **수익 모델 영향**: 없음(핵심 무료 루프). 단 **친구 신청 수락률(1순위 지표)을
  가장 크게 움직일 후보**다.
- **측정**: 후보 노출 수 / 선택 수 / **상호 일치율**. 상호 일치율이 친구 신청
  수락률보다 유의하게 높은지가 이 설계의 성패 판정 기준이다.

## O1. 백엔드 서버 도메인/HTTPS 설정

**배경**: 백엔드 아키텍처가 Spring Boot(지인 컴퓨터 24시간 구동)로 확정(2026-07-08,

TLS 인증서가 필요해짐(App Transport Security 정책상 HTTP 직접 접근 불가).

**결정할 것**:
1. 고정 IP/도메인 보유 여부 확인 — 없으면 DuckDNS 등 무료 동적 도메인 + Let's Encrypt
   무료 인증서로 해결 가능(포트포워딩만 되면 충분)
2. 리버스 프록시(Nginx/Caddy) 설정 — Caddy는 Let's Encrypt 인증서 자동 발급/갱신을
   내장하고 있어 설정이 더 간단함(권장)
3. 위 사항을 지인과 직접 협의 후 확정

**상태**: 미결정 — 사용자가 지인과 직접 협의 예정. 문서에는 설계(Caddy+Let's Encrypt
권장안)만 남겨둠, archive/DEV_STACK_PIPELINE.md 참조

## O2. 가입 수단 확장(카카오/구글/Apple/일반) + 전화번호 인증 — 기술 명세 미정

**배경**: 2026-07-19, 가입 수단을 카카오/구글/Apple/일반 4개로 확장하고 그 뒤에
전화번호 인증을 붙이는 것으로 제품/UX 흐름은 결정됨(archive/CONCEPT_v2.md
8절). 다만 이는 흐름 결정일 뿐, 실제 구현에 필요한 기술 명세는 아직 정해지지 않았다.

**결정할 것**:
1. 카카오/구글 OAuth 연동 방식 — 클라이언트 SDK(카카오 SDK, Google Sign-In)로
   토큰을 받아 서버가 검증하는 방식(현재 Apple 로그인과 동일 패턴)으로 통일할지
2. 전화번호 인증 수단 — SMS 인증(벤더: 알리고/Twilio/NHN Cloud 등) vs 다른 방식,
   비용 구조
3. DB 스키마 — `users` 테이블에 `phone_number`, `kakao_user_id`, `google_user_id`
   컬럼 추가 방식(Apple의 `apple_user_id` 패턴과 동일하게 갈지)
4. API 엔드포인트 설계 — `POST /api/v1/auth/kakao`, `/auth/google`, 전화번호 인증
   (`/auth/phone/verify` 등) 신설 필요
5. 전화번호 인증을 4개 가입 수단 모두에 공통 강제할지, 순서(가입 먼저 vs 인증 먼저)

**상태**: 미결정 — 제품/UX 흐름만 확정(archive/CONCEPT_v2.md 8절), 기술
명세는 착수 시점에 design/API_SPEC.md·design/DB_SCHEMA.sql·design/openapi.yaml에 반영 예정.
**v3 갱신(2026-08-15)**: design/DB_SCHEMA.sql `users`에 `kakao_user_id`, `google_user_id`,
`phone_number`, `phone_verified_at` 컬럼을 미리 반영해 뒀다(제품 결정은 확정이므로).
2~5번(SMS 벤더, 강제 여부, 순서)은 여전히 미결정.

## O3. 서비스 지역 게이팅을 유지할 것인가

**배경**: v2는 콜드스타트 대응으로 "선정 지역 유저에게만 매칭/채팅 노출"이라는 하드
게이팅을 Phase 1 필수로 두었다(ONBOARD-2). v3에서 이 명분이 약해졌다 — 친구 추천이
**반경 자동 확장**을 하기 때문에 "주변에 아무도 없음"이라는 빈 화면이 원천적으로
발생하지 않는다(product/CONCEPT.md 2.2).

**결정할 것**:
1. 하드 게이팅을 폐기하고 **전국 오픈 + 반경 자동 확장**만으로 갈 것인가
2. 아니면 게이팅을 유지하되 **"지역 밖에서는 후보 품질이 낮을 수 있다"는 안내 배너**
   수준의 소프트 게이팅으로 완화할 것인가
3. `service_areas` / `waitlist_signups` 테이블과 대기 등록 화면을 계속 유지할 것인가

**판단에 필요한 것**: 반경을 얼마나 넓히면 "친구"라고 부를 수 없을 만큼 멀어지는가.
현실적으로 **같이 산책하러 나갈 수 있는 거리**(도보/차량 10~15분)가 상한선이고, 이걸
넘어가면 추천해도 만남으로 이어지지 않는다. 즉 **반경 자동 확장에도 상한이 필요**하고,
그 상한을 넘는 지역 유저에게 무엇을 보여줄지가 결국 이 질문의 실질이다.

**잠정 권고**: 하드 게이팅 폐기(전국 오픈) + **반경 확장 상한(예: 5km) 설정** +
상한 내 후보가 없으면 대기 등록/커뮤니티로 유도. 이렇게 하면 매칭 외 기능(카드·산책기록·
커뮤니티·케어)은 전국에서 그대로 작동해 성장을 막지 않는다.

**상태**: 미결정 — **ONBOARD-2 티켓은 이 결정 전까지 착수 보류**

> **Q10과의 의존 관계 (2026-08-15)**: Q10이 해결되면서 반경 상한 5km를 **잠정값으로
> 채택**해 추천 점수 공식에 넣었다(`distance_score = 1 − distance_km / 5`,
> 확장 단계 `1→2→3→5km`). Q8이 다른 상한으로 결정되면
> **design/RECOMMENDATION.md의 `max-radius-km`와 `radius-steps-km`를 함께 갱신**해야
> 한다. 다행히 둘 다 `application.yml` 설정값이라 코드 변경은 필요 없다.

## O4. 동네 산책로 추천의 점진 활성화 임계치

**배경**: "동네 강아지들이 걸었던 경로를 집계해 좋은 길을 추천"(product/CONCEPT.md 3.2)은
동네에 산책 기록이 쌓이기 전에는 추천할 데이터가 없다. 데이터 3건으로 "이 동네 인기
코스"라고 부르면 신뢰를 잃는다.

**결정할 것**:
1. 특정 동네에서 이 기능을 켜는 최소 조건 (예: 반경 1km 내 **서로 다른 유저 N명**의

   같은 길을 50번 걸은 걸 "인기 코스"라고 할 수는 없다
2. 임계치 미달 동네에서 이 UI를 어떻게 처리할지 (숨김 / "아직 기록이 모이는 중" 표시)
3. 경로 집계 방식 — 원본 GPS 궤적을 그대로 겹칠지, 격자/도로 스냅으로 정규화할지
   (개인 산책 궤적이 그대로 노출되면 **집 위치가 추론될 수 있다** — 시작·종료 지점

처리)은 WALK-1 경로 저장 설계 시점에 미리 고려**해 두는 게 안전하다

## O5. 꼬동 파트너(점주 앱) — 형태 / 매장 확보 / 과금

**배경**: Phase 3의 매장 생태계는 **B2B2C**다. 지금까지의 순수 B2C 소셜 앱과 사업
성격이 다르고, 매장 발굴·계약·정산·CS라는 코드와 무관한 운영 업무가 새로 생긴다.
(v2 7.2절에서 이미 동일한 우려가 제기된 바 있다.)

**결정할 것**:
1. **형태** — 별도 네이티브 앱 vs 웹 대시보드. 웹이 개발·배포 비용이 훨씬 낮고
   점주는 PC/태블릿 사용 비중이 높다. **"전용 앱"이 요구사항인지, "전용 도구"가
   요구사항인지** 확인 필요
2. **매장 확보 전략** — 파일럿 매장 1곳을 어떻게 섭외할지(지인 소개 등).
   유저 콜드스타트와 **별개의 두 번째 콜드스타트**다
3. **과금** — 예약 건당 수수료 vs 점주 정액 구독. 수수료는 정산·환불·분쟁 운영
   부담이 크다(v2에서 산책 대행 수수료 모델이 기각된 이유와 같은 계열의 부담)
4. **매장 정보 초기 확보** — 점주 등록만 기다리면 지도가 텅 빈다. 공공데이터
   (동물병원 인허가 데이터 등)로 미등록 매장을 먼저 채우고 점주가 "내 매장 인증"으로
   가져가는 방식(당근 비즈프로필 패턴)을 검토할 가치가 있음
5. **예약 시 전달할 반려견 정보 범위** — 어디까지가 유용하고 어디부터가 과잉인지

**상태**: 미결정 — Phase 3 항목. **Phase 1 완주 전에는 착수하지 않는다**

## O6. 커머스 — 직접 판매(1P) 소싱 / 물류 / PG 구조

**배경**: **2026-08-22 모델 전환** — 중개(마켓플레이스)에서 **꼬동이 직접 매입해 파는
1P 커머스**로 바뀌었다(product/CONCEPT.md 3.10, 7절 "v3 이후 뒤집힌 결정").
유저는 보금자리 사진에 **자사 카탈로그 상품을 태그**하고, 그 태그가 상품 상세로 이어진다.

판매자 확보라는 콜드스타트는 사라졌지만, **재고·물류·반품이 새로 생겼다.**
아래 항목은 전부 그 대가에 관한 것이다.

**결정할 것**:
1. **상품 소싱** — 직접 매입 vs 위탁판매(재고 없이 주문 시 공급사 출고). **위탁으로
   시작하면 매입 자금과 재고 리스크 없이 수요 검증만 먼저 할 수 있다** — 1P를 처음부터
   다 만드는 것보다 훨씬 싼 1단계. (중개 시절의 "어필리에이트로 시작" 논리와 같은 구조)
2. **물류** — 자가 포장/발송 vs 3PL 위탁. **1인 운영에서 자가 발송은 주문량이 늘수록
   개발 시간을 직접 잠식한다.** Phase 4 착수 전에 3PL 단가를 먼저 확인할 것
3. **반품/교환/불량 CS** — 중개와 달리 **전부 운영자 책임**이다. 반품 배송비 정책,
   처리 리드타임, 불량 판정 기준
4. **PG / 법적 요건** — 결제대행사 선정, **통신판매업 신고**(중개업이 아니라 판매업),
   전자상거래법상 표시·광고 의무
5. **앱스토어 결제 정책** — 실물 상품은 IAP 대상이 아니라 외부 결제 가능하나,
   **패스권(디지털 재화)과 결제 흐름이 섞이지 않게 분리**해야 심사 이슈가 없다
6. **창작자 리워드 여부** — 태그된 상품이 팔릴 때 사진 게시자에게 적립금을 줄 것인가.
   **주는 순간 사진 도용이 수익성 있는 공격이 된다**(남의 사진을 퍼와 태그 → 적립금).
   준다면 이미지 중복 탐지·지급 유예·계정 이력 요건이 함께 필요하다. **안 주면 이 위험은 없다**

**상태**: 미결정 — Phase 4 항목

## O7. 패스권 상품 구성 · 가격

**배경**: 패스권(구독)은 **유저 밀도 없이도 작동하는 유일한 초기 수익 축**이라 MVP부터
켜기로 했다(product/CONCEPT.md 4절 ① 축, PASS-1).

**결정할 것**:
1. **티어 구성** — Free/Plus/Pro 3단계를 유지할지, Free/패스권 2단계로 단순화할지.
   유저가 적은 초기에 3단계는 선택 부담만 늘릴 수 있다
2. **무료 마릿수 한도** — Free에서 몇 마리까지 등록 가능한가. **1마리로 두면 다견종
   가구가 온보딩에서 막히고, 3마리로 두면 전환이 거의 안 일어난다.** 실제 다견종 가구
   비율을 근거로 정할 것
3. **카드 커스터마이징 범위** — 무료 템플릿 몇 종 / 유료 몇 종
4. **가격** — 월 구독 vs 연 구독 vs 영구 패스. 원화 가격대
5. **App Store Connect 상품 ID 체계**

**상태**: 미결정 — PASS-1 착수 전 필요
